# Runic Translations 0.12.0

Install matching `0.12.0` packages from NuGet and npm: the eight NuGet packages
(`Runic.Translations`, `.Build`, `.CommandLine`, `.Hosting`, `.Tooling`, `.Wpf`,
`.Templates` and the `dotnet-runic-translations` tool) and the three npm
packages (`@runic-artifex/vite-plugin-runic-translations`,
`@runic-artifex/translations-svelte` and `@runic-artifex/translations-sveltekit`).

0.12.0 is the Translations release of the 0.20 release train: Runic Translations
0.12.0, then Runic SDK 0.20.0, then the editor extensions from runic-editors
0.20.0. Runic Command Line is not part of this train:
**`Runic.Translations.CommandLine` 0.12.0 needs Runic Command Line 0.13**, as
0.11.0 did. Translations 0.12.0 and Runic SDK 0.20.0 were restored, built and
run together with warnings as errors before either was published.

This release is about working on translations in the running page. Under
`vite dev` an edited message now updates in place instead of reloading the
page, a page can read and write a message through the dev server, and an
inspector can tell which message an element shows; Runic SDK 0.20's Runic
Inspect uses all three to edit translations on the page. Go to Definition on
`m.key()` opens the message's source, and the VS Code and Visual Studio
extensions now release from runic-editors.

Until 1.0 a new minor may contain breaking changes. This release removes no
API; it changes how the dev server handles edits. See
[Upgrading from 0.11](#upgrading-from-011) and
[Versions before 1.0](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/eng/release/README.md#versions-before-10).

## Highlights

- **Edited messages update in place under `vite dev`**, keeping the page's
  state; changes that need it still reload, with the reason logged
  ([details](#edited-messages-update-in-place-during-development)).
- **A write API for in-page translation editing** on the dev server: read a
  message in every locale and write one locale's text back, source-preserving
  and loopback only by default
  ([details](#a-write-api-for-in-page-translation-editing)).
- **Message markers** tell an inspector which message an element on the page
  shows ([details](#message-markers-for-inspectors)).
- **Go to Definition from `m.key()`** opens the message in the base locale's
  source file, through a declaration map and with no extension
  ([details](#go-to-definition-from-mkey-to-the-messages-source)).
- **The editor extensions release from
  [runic-editors](https://github.com/Runic-Artifex/runic-editors)**; Translations
  releases no longer carry `.vsix` files
  ([details](#the-editor-extensions-release-from-runic-editors)).

## Edited messages update in place during development

([#176](https://github.com/Runic-Artifex/runic-translations-sdk/issues/176))
Under `vite dev`, `@runic-artifex/vite-plugin-runic-translations` no longer
reloads the page when a message's text changes. It compares each regeneration
with the previous one:

- **Text edits update in place:** a message's text in any locale, a plural or
  selector variant, text inside inline markup or a document, and the
  pseudo-locales. The browser fetches only the edited messages' modules, which
  hand their new text to the modules the page already holds; the runtime, the
  catalog's resolvers and installed overlays stay, and so does the page's state.
  The SSR environment gets the same update. This includes the application's
  overrides of library catalogs regenerated with `dependencies: "auto"`.
- **The page formats again** through a new global text-change channel,
  `globalThis[Symbol.for("runic.translations.text")]`
  (`{ version: 1, revision, listeners }`), documented in
  [the ESM guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/docs/guides/translations/esm.md#text-changes-during-development).
  `useMessageLocale` from `@runic-artifex/translations-svelte` follows it, so
  Svelte and SvelteKit applications without runic-sdk update in place; runic-sdk's
  text helpers follow it from their next release. The shared locale channel is
  unchanged.
- **Everything else reloads, with the reason logged:** added, removed or renamed
  messages, changed inputs, markup or content kinds, added or removed source
  files and runic.json changes, for example
  `[runic-translations] page reload: messages were added, removed or renamed in catalog 'app'`.
  The plugin now sends the reload itself, once per environment.
- **A page that follows no text changes reloads,** as before, rather than
  showing stale text.
- **A compile error** keeps the last good text under Vite's error overlay; the
  next good save updates in place.
- **Rapid saves** of one or several files are compiled in turn and the last one
  always wins, including a save that Vite's watcher drops because it follows
  another within 50 ms.
- **Manifest mode** (a `dotnet build` that owns generation) gets the same
  comparison, so edits it regenerates update in place too.

The dev server no longer watches the generated `.d.ts` files, which the plugin
writes only when their content changes. Framework plugins that reload on every
`.d.ts` change, such as Analog's, no longer turn each message edit into a reload.

Production builds are unchanged: `vite build` produces the same bytes as with
0.11.0 for the same inputs, and the generated ESM is the same.

## A write API for in-page translation editing

([#178](https://github.com/Runic-Artifex/runic-translations-sdk/issues/178))
Under `vite dev`, `@runic-artifex/vite-plugin-runic-translations` offers
`/__runic-translations/message`, so a page can edit a translation in place:
runic-sdk's Runic Inspect selects a text, shows its message in every locale and
writes the edit back.

- **`GET`** reads a message of the application's catalog, or of a library
  catalog regenerated with `dependencies: "auto"`, in every locale: its text as
  authored, its inputs and plural or selector variants, where each locale
  defines it, and the SHA-256 of the file a write changes.
- **`POST`** writes one locale's whole message text (plural, selector, markup
  and document messages as their whole source). It is compiled with the rest of
  the catalog first and refused with its diagnostics (422) when it does not
  compile; a file that changed since it was read is refused (409) with the
  current message. The page then updates in place, as on a save.
- **Source-preserving:** the write goes through `runic-translations serve`,
  which gains `message` and `set-message` requests, and the Translations Editor's
  writer, so only the message's text changes and the file keeps its formatting,
  comments, line endings and order. A locale without the message gets it
  inserted beside the base locale's.
- **Library catalogs:** a write goes to the application's override,
  `translations/overrides/<catalog>/<locale>.rmf2`, by the rules of
  `runic-translations overrides add --key` (with its review entry, and listing the
  catalog in runic.json `overrides` when needed); the installed package is never
  written.
- **On by default, loopback only:** the API exists only on the dev server and
  accepts same-origin requests from the same machine. `inPageEditing: { allow:
  [...] }` or the `RUNIC_DEV_ALLOW` environment variable admit other hosts and
  networks (addresses, IPv4/IPv6 CIDR such as a Tailscale network, host names).
  `RUNIC_DEV_ALLOW` is the same setting vite-plugin-runic 0.20 reads for Runic
  Inspect, so one variable covers both plugins; `RUNIC_TRANSLATIONS_EDIT_ALLOW`
  is accepted too;
  `inPageEditing: false` turns it off. Vite's host check still applies. Production
  builds are byte for byte the same with or without it.

See "In-page editing API" in the plugin's README and
[In-page translation editing](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/docs/guides/translations/esm.md#in-page-translation-editing).

## Go to Definition from `m.key()` to the message's source

([#177](https://github.com/Runic-Artifex/runic-translations-sdk/issues/177))
`generate --emit-esm` writes a declaration map, `messages.d.ts.map`, beside
`messages.d.ts`. Go to Definition on `m.key()`, or on an input name in its
argument object, now opens the message's entry in the base locale's `.rmf2` or
`.mf2` file at the line of its key, in any editor whose TypeScript support
follows declaration maps (VS Code and Visual Studio through `tsserver`), with no
extension. Before, it stopped in `messages.d.ts`.

- The map points at the entry whose text the base locale uses. In a library
  catalog that the Vite plugin regenerates with `dependencies: "auto"`, an
  overridden key opens the application's override file and every other key the
  library's packed source.
- `@runic-artifex/vite-plugin-runic-translations` writes the matching
  `virtual.d.ts.map` and `dependencies/<catalog>.d.ts.map`, so imports from
  `virtual:runic-translations/<catalog>` navigate the same way.
- The JavaScript output is unchanged. `messages.d.ts` gains one
  `//# sourceMappingURL` line. The map's `sources` are relative paths, and
  `web-module-manifest-v3.json` does not list the map, so plugins that predate
  it still load the catalog.

See [Editor navigation](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/docs/guides/translations/esm.md#editor-navigation).

## The editor extensions release from runic-editors

([#181](https://github.com/Runic-Artifex/runic-translations-sdk/issues/181))
The VS Code and Visual Studio 2026 extensions moved, with their history, to
[Runic-Artifex/runic-editors](https://github.com/Runic-Artifex/runic-editors),
which builds, tests and releases them on its own. The VS Code extension there is
becoming one Runic extension for Translations and the Runic SDK
([runic-editors#2](https://github.com/Runic-Artifex/runic-editors/issues/2)).

- **Translations releases no longer carry `.vsix` assets.** From 0.12.0 the
  GitHub release has the NuGet and npm packages and the SBOM only, and the SBOM
  and attestations no longer describe extensions. Install
  `runic-translations.vsix` and `runic-translations-visualstudio.vsix` from the
  [runic-editors releases](https://github.com/Runic-Artifex/runic-editors/releases);
  the files attached to releases up to 0.11.0 stay where they are.
- **The language server stays here.** `runic-translations lsp` in
  `dotnet-runic-translations` is the server both extensions run from the
  project's local tool, as before. The new
  [language server guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/docs/guides/translations/language-server.md)
  describes its protocol, how editors launch it and which versions work
  together. It stays outside the 1.0 compatibility rules until the production
  language server (2.0).

## Message markers for inspectors

([#183](https://github.com/Runic-Artifex/runic-translations-sdk/issues/183))
Under `vite dev`, the text-change channel gains a `markers` member, so an
inspector can tell which message an element on the page shows. runic-sdk's
Runic Inspect uses it in select mode
([runic-sdk#956](https://github.com/Runic-Artifex/runic-sdk/issues/956)).

- `markers.set(true)` turns marker mode on and renders the page again, as a
  text edit does. Every `m.key()` call then puts an invisible marker in front of
  its text (the first text of an inline or document message) that names the
  message's catalog, key and locale. `markers.decode(text)` lists the messages a
  text contains, and `markers.strip(text)` removes the markers.
  `markers.set(false)` renders the plain text again.
- Marker mode is off unless an inspector turns it on, so text, `textContent`,
  copied text and tests are unchanged. The markers are invisible format
  characters (U+2061–U+2064) that take no width.
- It is part of the serve-only rewrite of message modules. The generated
  runtime and production builds are unchanged.

See [Message markers](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/docs/guides/translations/esm.md#message-markers).

## Upgrading from 0.11

Update every Runic Translations package, NuGet and npm, to 0.12.0 together.
Runic Command Line stays at 0.13.

- **The VS Code and Visual Studio extensions:** install them from the
  [runic-editors releases](https://github.com/Runic-Artifex/runic-editors/releases)
  (0.20.0 with this train) instead of from a Translations release. They still run
  `runic-translations lsp` from the project's local `dotnet-runic-translations`
  tool, so keep that tool at the project's Translations version.
- **Libraries packed with `Runic.Translations.Build` 0.11** depend on
  `Runic.Translations` `[0.11.0, 0.12.0-0.0)`, so an application on the 0.12.0
  runtime gets NuGet warning `NU1608`. Pack a library update with 0.12.0, as for
  every Runic Translations minor (see
  [Versions](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/docs/guides/translations/libraries.md#versions)).

### Behaviour and output changes

- **Under `vite dev` a text edit no longer reloads the page.** Code that reads
  a message's text once and keeps it, outside `m.key()` calls that run again
  and outside `useMessageLocale`, keeps showing the old text until the next
  reload; follow the text-change channel
  (`globalThis[Symbol.for("runic.translations.text")]`) to format again. A page
  that loads no module following the channel reloads as before. The dev server
  also no longer watches the generated `.d.ts` files. Production builds are
  unchanged.

- **The dev server answers `/__runic-translations/message`** by default, to
  same-origin requests from the same machine only, and a `POST` there writes
  the project's `.rmf2` files. Set `inPageEditing: false` in the plugin's options
  to turn it off; `inPageEditing: { allow: [...] }` or `RUNIC_DEV_ALLOW` admit
  other hosts. `vite build` and `vite preview` don't have it.

## Release engineering

- The release has the NuGet and npm packages and the SBOM only; its SBOM and
  attestations no longer list the `.vsix` files, which runic-editors attests
  for its own releases.
- Release notes are written as one fragment file per pull request under
  `eng/release/notes/<version>/` and assembled by the release pull request
  (`eng/release/notes.mjs`, D066.33); Publish preview stops while a version
  still has fragments.
