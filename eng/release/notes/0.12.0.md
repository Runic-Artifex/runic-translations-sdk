# Runic Translations 0.12.0

## Edited messages update in place during development

([#176](https://github.com/Runic-Artifex/runic-translations-sdk/issues/176))
Under `vite dev`, `@runic-artifex/vite-plugin-runic-translations` no longer
reloads the page when a message's text changes. It compares each regeneration
with the previous one:

- **Text edits update in place:** a message's text in any locale, a plural or
  selector variant, text inside inline markup or a document, and the
  pseudo-locales. The browser fetches only the edited messages' modules, which
  hand their new text to the modules the page already holds; the runtime, the
  catalog's resolvers and installed overlays stay, and so does the page's state.
  The SSR environment gets the same update. This includes the application's
  overrides of library catalogs regenerated with `dependencies: "auto"`.
- **The page formats again** through a new global text-change channel,
  `globalThis[Symbol.for("runic.translations.text")]`
  (`{ version: 1, revision, listeners }`), documented in
  [the ESM guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/docs/guides/translations/esm.md#text-changes-during-development).
  `useMessageLocale` from `@runic-artifex/translations-svelte` follows it, so
  Svelte and SvelteKit applications without runic-sdk update in place; runic-sdk's
  text helpers follow it from their next release. The shared locale channel is
  unchanged.
- **Everything else reloads, with the reason logged:** added, removed or renamed
  messages, changed inputs, markup or content kinds, added or removed source
  files and runic.json changes, for example
  `[runic-translations] page reload: messages were added, removed or renamed in catalog 'app'`.
  The plugin now sends the reload itself, once per environment.
- **A page that follows no text changes reloads,** as before, rather than
  showing stale text.
- **A compile error** keeps the last good text under Vite's error overlay; the
  next good save updates in place.
- **Rapid saves** of one or several files are compiled in turn and the last one
  always wins, including a save that Vite's watcher drops because it follows
  another within 50 ms.
- **Manifest mode** (a `dotnet build` that owns generation) gets the same
  comparison, so edits it regenerates update in place too.

The dev server no longer watches the generated `.d.ts` files, which the plugin
writes only when their content changes. Framework plugins that reload on every
`.d.ts` change, such as Analog's, no longer turn each message edit into a reload.

Production builds are unchanged: `vite build` produces the same bytes as with
0.11.0 for the same inputs, and the generated ESM is the same.

## Go to Definition from `m.key()` to the message's source

([#177](https://github.com/Runic-Artifex/runic-translations-sdk/issues/177))
`generate --emit-esm` writes a declaration map, `messages.d.ts.map`, beside
`messages.d.ts`. Go to Definition on `m.key()`, or on an input name in its
argument object, now opens the message's entry in the base locale's `.rmf2` or
`.mf2` file at the line of its key, in any editor whose TypeScript support
follows declaration maps (VS Code and Visual Studio through `tsserver`), with no
extension. Before, it stopped in `messages.d.ts`.

- The map points at the entry whose text the base locale uses. In a library
  catalog that the Vite plugin regenerates with `dependencies: "auto"`, an
  overridden key opens the application's override file and every other key the
  library's packed source.
- `@runic-artifex/vite-plugin-runic-translations` writes the matching
  `virtual.d.ts.map` and `dependencies/<catalog>.d.ts.map`, so imports from
  `virtual:runic-translations/<catalog>` navigate the same way.
- The JavaScript output is unchanged. `messages.d.ts` gains one
  `//# sourceMappingURL` line. The map's `sources` are relative paths, and
  `web-module-manifest-v3.json` does not list the map, so plugins that predate
  it still load the catalog.

See [Editor navigation](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/docs/guides/translations/esm.md#editor-navigation).

## The editor extensions release from runic-editors

([#181](https://github.com/Runic-Artifex/runic-translations-sdk/issues/181))
The VS Code and Visual Studio 2026 extensions moved, with their history, to
[Runic-Artifex/runic-editors](https://github.com/Runic-Artifex/runic-editors),
which builds, tests and releases them on its own. The VS Code extension there is
becoming one Runic extension for Translations and the Runic SDK
([runic-editors#2](https://github.com/Runic-Artifex/runic-editors/issues/2)).

- **Translations releases no longer carry `.vsix` assets.** From 0.12.0 the
  GitHub release has the NuGet and npm packages and the SBOM only, and the SBOM
  and attestations no longer describe extensions. Install
  `runic-translations.vsix` and `runic-translations-visualstudio.vsix` from the
  [runic-editors releases](https://github.com/Runic-Artifex/runic-editors/releases);
  the files attached to releases up to 0.11.0 stay where they are.
- **The language server stays here.** `runic-translations lsp` in
  `dotnet-runic-translations` is the server both extensions run from the
  project's local tool, as before. The new
  [language server guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.12.0/docs/guides/translations/language-server.md)
  describes its protocol, how editors launch it and which versions work
  together. It stays outside the 1.0 compatibility rules until the production
  language server (2.0).
