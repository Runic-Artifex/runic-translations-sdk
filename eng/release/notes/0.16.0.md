# Runic Translations 0.16.0

Install matching `0.16.0` packages from NuGet and npm: the eight NuGet packages
(`Runic.Translations`, `.Build`, `.CommandLine`, `.Hosting`, `.Tooling`, `.Wpf`,
`.Templates` and the `dotnet-runic-translations` tool) and the three npm
packages (`@runic-artifex/vite-plugin-runic-translations`,
`@runic-artifex/translations-svelte` and `@runic-artifex/translations-sveltekit`).

0.16.0 is the Translations step of the 0.24 release train (Runic Command Line
0.15.0, then Translations 0.16.0, then the Runic SDK 0.24.0).
**`Runic.Translations.CommandLine` 0.16.0 needs Runic Command Line 0.15.**

This release prepares the Runic Artifex rename (0.17): it already reads library
catalogs packed in the renamed format and ships the build's old-name guards,
still empty. From runic-sdk 0.24 the tool also runs as `dotnet runic
translations`, and the capability matrix gets a version 2 with an open set of
implementations. It changes no API and no generated code; the one required
change is the Command Line 0.15 pairing.

Until 1.0 a new minor may contain breaking changes. See
[Upgrading from 0.15](#upgrading-from-015) and
[Versions before 1.0](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.16.0/eng/release/README.md#versions-before-10).

## Highlights

- **Ready for the Runic Artifex rename.** The build, the `overrides` CLI, the
  language server and the editor read a package's library catalog in the
  renamed format (`rax/<catalog>/rax.json` with `*.ramf2` sources) as well as
  the current one, so a library can move first and no library has to republish
  when an application updates
  ([details](#library-catalogs-in-the-renamed-format)).
  `Runic.Translations.Build` ships the guards that will name the new name for a
  former package ID, MSBuild name or environment variable; this release lists
  no name yet
  ([details](#old-name-guards-for-the-runic-artifex-rename)).
- **`dotnet runic translations`.** From runic-sdk 0.24 the Runic core tool runs
  `runic-translations` as its `translations` extension, with the same arguments
  and exit code; `runic-translations --extension-info` answers the core's
  `doctor`. The package and the command keep their names
  ([details](#dotnet-runic-translations-runs-this-tool)).
- **Capability matrix version 2.** `capabilities-v2.json` lists the
  implementations of the Translations contract as an open set, each with its
  status, so a new runtime such as Rust is added without a new matrix version.
  Version 1 is frozen and now validates against its own schema
  ([details](#capability-matrix-version-2-315)).

## Capability matrix version 2 ([#315](https://github.com/Runic-Artifex/runic-translations-sdk/pull/315))

`specs/translations/capabilities-v2.json` lists the implementations of the Translations contract as an open set of
keys, each with its status (`development`, `preview` or `stable`) and the source of its localized dates and times, so a
new implementation such as a Rust runtime is added without a new matrix version. `runic-translations schema` writes
its schema, `capabilities-v2.schema.json`, beside the others. Version 1 (`capabilities-v1.json`, with the closed
`backends` tuple `dotnet`, `esm`) is frozen and still generated. See the
[capability matrix](../../../specs/translations/capabilities.md).

## `dotnet runic translations` runs this tool

From runic-sdk 0.24, `dotnet runic translations …` runs `runic-translations …` as an extension of the Runic core tool,
with the arguments unchanged and this tool's exit code. For the core's `doctor`, the tool answers
`runic-translations --extension-info` with one JSON line: `name` (`translations`), `version` (the release that
`--version` reports) and `extensionProtocol` 1, plus `command` and `package`. Nothing else changes: the package
`dotnet-runic-translations` and the command `runic-translations` keep their names in this release. See
[Run under `dotnet runic`](../../../tools/dotnet-runic-translations/README.md#run-under-dotnet-runic).

## Old-name guards for the Runic Artifex rename

`Runic.Translations.Build` ships the old-name guards of the rename (D079.11) in
`build/Runic.Translations.RenamedNames.targets`, generated from `eng/rename/old-names.json`. They fail a build that has
a package of a former ID in its package graph (`RTR0110`), sets a former MSBuild name (`RTR0086`, as for the names from
before the `Runic` prefix) or has a former environment variable set (`RTR0111`), each once, with an error that names the
new name; the package error also names `rax migrate`. This release lists no name, so nothing reports them yet; the
rename release fills the lists, and the guards stay through 1.0.x. See
[RTR0110](../../../docs/guides/translations/diagnostics.md#rtr0110).

## Library catalogs in the renamed format

The Runic Artifex rename (0.17) renames a packed library catalog. The new spelling is `rax/<catalog>/rax.json` with
`*.ramf2` sources, which write Runic's MF2 namespace `rax:` (`:rax:uuid`, `{#rax:link}`), declared as a
`RaxTranslationsPackedCatalog` item. This release already reads a package's catalog in either format: in the build, the
`overrides` CLI, the language server and the editor. A package that ships both is read in the new format. The
`Runic.Translations.CommandLine` adapter takes the `runic-command-line` catalog from `translations/rax.json` when the
Command Line package ships it there. So Command Line can move to the new format before Translations does, and no library
has to republish when an application updates. Packing, an application's own catalog and its override sources are
unchanged, and `rax:` is read only in `.ramf2` sources. From the rename on, a package catalog in the former format still
builds and warns with `RTR0109`; nothing reports it in this release. See
[Library catalog formats](../../../docs/guides/translations/libraries.md#library-catalog-formats).

## Upgrading from 0.15

Update every Runic Translations package, NuGet and npm, to 0.16.0 together, and
Runic Command Line to 0.15.

- **Runic Command Line 0.15.** `Runic.Translations.CommandLine` 0.16 pairs with
  Runic.CommandLine 0.15: its package depends on `Runic.CommandLine`
  `[0.15.0, 0.16.0-0.0)`, so update both together; 0.15.x of the adapter stays
  on Command Line 0.14. Command Line 0.15 adds and changes no text keys, so the
  `runic-command-line` catalog and its English and German text are unchanged,
  and your overrides and packs keep working. Help and usage errors change in
  every language: a command's and a group's help no longer list `--version`
  (`Version anzeigen` in German), which only root help keeps; a root command's
  usage error ends with root help's usage line and
  `Weitere Informationen erhalten Sie mit "<application> --help".`; and a root
  command's name is no longer suggested for a mistyped command. Update tests
  that compare such help or standard error text. See the
  [Command Line 0.15 release notes](https://github.com/Runic-Artifex/runic-cli-sdk/releases/tag/v0.15.0).

## Fixes

- The capability matrix version 1 validates against its own schema
  ([#316](https://github.com/Runic-Artifex/runic-translations-sdk/issues/316)). The matrix has always listed
  language-script locales such as `az-Arab`, which the schema's locale tag pattern `^[a-z]{2,8}$` rejected.
  `capabilities-v1.schema.json` now accepts a language or language-script locale, as version 2 does; the format is
  unchanged, and every document that validated before still validates.
- Runic.Translations.Build works with Visual Studio's MSBuild, which runs on .NET Framework
  ([runic-sdk#1299](https://github.com/Runic-Artifex/runic-sdk/issues/1299)). Its targets computed paths with
  `Path.GetFullPath(string, string)`, `Path.GetRelativePath` and `Path.TrimEndingDirectorySeparator`, which only .NET
  has, so a build in Visual Studio failed with MSB4186, for example with `RunicTranslationsCldrSubset` set. They now use
  MSBuild's `NormalizePath`, `NormalizeDirectory` and `MakeRelative`, which give the same paths in Visual Studio and
  `dotnet build`.

## Release engineering

- A release's generated list of pull requests starts at the previous SDK tag, for example `v0.15.0` for 0.16.0
  ([#278](https://github.com/Runic-Artifex/runic-translations-sdk/issues/278)): `ci-artifact.mjs release` passes the
  highest `v<version>` tag below the new one to `gh release create --notes-start-tag`. GitHub would otherwise start at
  the latest release before the new tag, which can be a Translations Editor release (`editor-v<version>`).
- The macOS and Windows jobs run only for changes that can behave differently on those platforms: `eng/ci/macos-paths.txt`
  and `eng/ci/windows-paths.txt` now list platform globalization, Windows path rules, the editor's native host and
  toolchain pins, and an ordinary push to `main` follows them as a pull request does. Nightly and dispatched runs and
  the push run of a version or release commit still run every job and upload the `ci-full-run` artifact. Publish
  preview takes a release's packages only from such a full green run of its commit, and fails with the command that
  dispatches one when the commit has only an ordinary push run.
