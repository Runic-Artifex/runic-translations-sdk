# Runic Translations 0.7.0-preview.3

## Generated C# catalogs

- The generated C# catalog embeds each locale's messages as UTF-8 data and reads
  a locale when a manager or provider first needs it, with the locales it falls
  back to. It used to build every message of every locale in one method, which
  the JIT compiled whole in each process that created a manager: for a catalog
  of about 1,300 messages in two locales, about 300 ms of JIT and 210 MiB peak
  memory before the first message. The same catalog now takes about 90 ms of
  JIT and 60 to 70 MiB, and a process that formats only English never reads
  German. Rebuild to pick up the change; the generated API is unchanged
  ([#87](https://github.com/Runic-Artifex/runic-translations-sdk/issues/87)).
- `CompiledTranslationLocale.CreateDeferred` and
  `CompiledTranslationLocale.ReadRmf2Values` are the runtime side of this, for
  generated code. A catalog with deferred locales validates each one on its
  first snapshot; invalid data fails that snapshot with an
  `InvalidOperationException`. Catalogs built from locales with their values
  are validated in the constructor, as before.
- A `TranslationProject` outside the C# project's directory, such as
  `../Frontend/translations/runic.json`, now builds. Its sources reached the
  compiler under a different path than the project and failed with `RTR0052`.
- New example and guide section: [strings outside the Views](https://github.com/Runic-Artifex/runic-translations-sdk/blob/main/docs/guides/translations/runic-desktop.md#strings-outside-the-views),
  a C# tray process that formats its frontend's catalog and is published with
  NativeAOT in CI.

## Svelte and Vite apps

- New `useMessageLocale(configureLocaleResolver, locale)` in
  `@runic-artifex/translations-svelte/translations` makes the generated `m.*()`
  calls follow a locale the application owns, such as a ViewModel's language
  setting. Templates, `$derived` and `$effect` that call a message update in
  place when it changes, so the page no longer needs `{#key locale}`. Pass a
  getter over Svelte state or a `SvelteLocale`
  ([#86](https://github.com/Runic-Artifex/runic-translations-sdk/issues/86)).
- A decimal input (`:number`, `:runic:relative-time`) now accepts a finite
  JavaScript `number`, read as the decimal `String(value)` writes:
  `m.hours({ count: 1.5 })`. It used to require a decimal string or
  `decimal("...")` and threw `TypeError` for a number. The generated
  declarations type such inputs as `Rmf2Decimal | string | number`, and
  `createTextReference` accepts numbers too. `NaN` and the infinities are
  rejected. Regenerate ESM output to pick up the change (#86).
- `LocalizedInline` and `LocalizedDocument` work in a Vite and Svelte app
  without SvelteKit, such as a Runic application's frontend. The Vite quick
  start gains a [Svelte without SvelteKit](https://github.com/Runic-Artifex/runic-translations-sdk/blob/main/docs/guides/translations/quickstart-vite.md#svelte-without-sveltekit)
  section, and the packaged-consumer check builds that app from a clean checkout
  ([#88](https://github.com/Runic-Artifex/runic-translations-sdk/issues/88)).
- The Vite plugin writes `.runic/translations/virtual.d.ts` when Vite runs, so a
  type check on a clean checkout must come after the build: use
  `vite build && svelte-check` (or `tsc`, `vue-tsc`). The Vite quick start and
  the plugin README now say so
  ([#84](https://github.com/Runic-Artifex/runic-translations-sdk/issues/84)).

## Smaller generated ESM

- Message modules are compact. A message that is text and plain placeholders
  (`{$name}`) is written as its parts, other messages as minified AST JSON
  instead of indented JSON, and a locale whose message comes from its fallback
  shares that object instead of repeating it. For nix-manager's catalog (about
  1,300 messages in two locales), the minified bundle of every message shrank
  from 2.0 MB to 0.93 MB, of which 0.32 MB is `runtime.js`; gzipped, from 144 kB
  to 137 kB. Messages format exactly as before. Regenerate ESM output to pick
  up the change
  ([#85](https://github.com/Runic-Artifex/runic-translations-sdk/issues/85)).

## Importing text-keyed catalogs

- New `runic-translations import-text` command
  ([#85](https://github.com/Runic-Artifex/runic-translations-sdk/issues/85)). It
  imports a catalog keyed by base-language text, such as
  `{ "Remove user {name}": "Benutzer {name} entfernen" }`, into the RMF2 group
  `<project>/<group>/`:
  `runic-translations import-text --group stored --base untranslated.json --table de=de.json`.
  It writes `<baseLocale>.rmf2`, one `<locale>.rmf2` per `--table` and
  `base-text.json`, then validates the project like `validate`; `--dry-run`
  validates the planned files without writing them.
- `{name}` placeholders become `{$name}`, other `{`, `}` and `\` are escaped, and
  text that an unquoted pattern would change (outer whitespace, a leading `.`, a
  newline) is written as a quoted pattern. A translation that uses a placeholder
  its base text lacks, or a table value that is not a string, is the new
  `RCLI9014` error: the command exits with 1 and writes nothing.
- Keys are generated from the first seven ASCII words of each base text, such as
  `remove_user`, with `_2`, `_3` on collision. A re-import keeps the key of every
  text that is still present, gives new texts new keys and lists the removed
  ones, so generated message names stay stable.
- `base-text.json` maps each base text to its generated message key
  (`"Remove user {name}": "stored_remove_user"`), so an application can look up
  text it stored in the base language. New data should store text references
  instead. See
  [Import a text-keyed catalog](https://github.com/Runic-Artifex/runic-translations-sdk/blob/main/docs/guides/translations/rmf2.md#import-a-text-keyed-catalog).
- `Runic.Translations.Tooling`: `TranslationsToolCommandModule.ImportText` and
  the `TranslationsToolCommandRequest.Group`, `Tables` and `BaseTexts` init
  properties carry the new command. The positional constructor of
  `TranslationsToolCommandRequest` is unchanged.
