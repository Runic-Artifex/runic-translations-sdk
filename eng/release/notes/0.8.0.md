# Runic Translations 0.8.0

Install matching `0.8.0` packages from NuGet and npm: the seven NuGet packages
(`Runic.Translations`, `.Build`, `.CommandLine`, `.Tooling`, `.Wpf`,
`.Templates` and the `dotnet-runic-translations` tool) and the three npm
packages (`@runic-artifex/vite-plugin-runic-translations`,
`@runic-artifex/translations-svelte` and `@runic-artifex/translations-sveltekit`).
Tested with Runic Command Line 0.9.0.

0.8.0 is the first plain version: Runic Translations no longer uses
`-preview.N` suffixes. Until 1.0 a new minor may contain breaking changes, each
listed here with its upgrade steps, and a patch only fixes or adds. Releases are
still previews, marked as GitHub prereleases. 1.0.0 will be preceded by
`1.0.0-rc.N` releases. See
[Versions before 1.0](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.8.0/eng/release/README.md#versions-before-10)
and [Versioning and support from 1.0](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.8.0/eng/release/README.md#versioning-and-support-from-10).

This release settles the API for 1.0. `Runic.Translations.Tooling` becomes a
stable package with a smaller public surface: the command plumbing, workspace
transactions, MF2 syntax tree and language service are internal. Generated-code
support moves to `Runic.Translations.Generated`. The MSBuild names get a
`Runic` prefix, and old names fail with `RTR0086`. The npm packages require
Vite 8.3.3 and Svelte 5.57.1, accept Node 26 and have one import path per
export. `runic-translations` selects its output with `--format`, uses the Runic
exit codes and its own diagnostic codes, and reads `@file` response files
through Runic Command Line 0.9.0. JSON schemas now describe its payloads. See
[Upgrading](#upgrading), [Behaviour changes](#behaviour-changes) and
[Security](#security).

## Upgrading

Update every Translations package and the `dotnet-runic-translations` tool to
0.8.0 together: `Runic.Translations.Build` reads the tool's new exit codes (see
[Command-line tools](#command-line-tools)). Rebuild after updating; the build
regenerates catalog code into the new generated-code namespace. Package
validation, the `PublicAPI` files and each pull request's description list the
changes in full; the tables below cover what application code usually touches.

### Build properties and build errors

- Every MSBuild property, item and metadata name of `Runic.Translations.Build`
  starts with `Runic`. A project that still sets an old name fails with
  [`RTR0086`](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.8.0/docs/guides/translations/diagnostics.md#rtr0086),
  which names the replacement
  ([#110](https://github.com/Runic-Artifex/runic-translations-sdk/pull/110)).
- `TranslationsEmitTypeScript`, `TranslationsEmitTemplateManifest` and
  `TranslationsEmitCpp` are removed: they selected emitters that do not exist.
  Setting one fails with `RTR0086`
  ([#110](https://github.com/Runic-Artifex/runic-translations-sdk/pull/110)).
- MSBuild errors carry their code (`RTR0020`, `RTR0002`, `RTR0086`) as the
  error code instead of in the message text
  ([#110](https://github.com/Runic-Artifex/runic-translations-sdk/pull/110)).
- `Runic.Translations.Build` treats tool exit code 2, not 1, as translation
  diagnostics. A Build package from an earlier release run with the 0.8.0 tool
  still fails the build on translation errors, but adds a generic "exited with
  code 2" error
  ([#104](https://github.com/Runic-Artifex/runic-translations-sdk/pull/104)).

### Runtime and generated code

- Generated-code support moved to `Runic.Translations.Generated`
  (`CompiledRmf2*`, `TranslationsCompatibility` and the new
  `GeneratedCatalogSupport` with the factories generated catalogs call). It is
  hidden from IntelliSense and stays binary compatible for code an earlier
  release of the same major generated, but it is not application API.
  Regenerate after upgrading; the build does this
  ([#109](https://github.com/Runic-Artifex/runic-translations-sdk/pull/109)).
- Generated readable surfaces implement the new `IReadableMessages`
  ([#109](https://github.com/Runic-Artifex/runic-translations-sdk/pull/109)).
- `ITranslationManager.SnapshotPublished` replaces `ITranslationSnapshotNotifier`.
  Custom managers raise it for locale switches and refreshes
  ([#109](https://github.com/Runic-Artifex/runic-translations-sdk/pull/109)).
- `TranslationPackException` carries its `Reason` and `RejectionId`
  (`RTR0023/<reason>`) and the constant `DiagnosticId`; the
  `TranslationPackFailure` helpers for a pack exception are removed
  ([#109](https://github.com/Runic-Artifex/runic-translations-sdk/pull/109)).
- Transport writers emit version 2 only, in .NET and in generated ESM.
  Version 1 stays readable
  ([#109](https://github.com/Runic-Artifex/runic-translations-sdk/pull/109)).
- `MarkupBinding` and `InlineMarkupBinding` are a closed set: they cannot be
  derived from outside the package
  ([#109](https://github.com/Runic-Artifex/runic-translations-sdk/pull/109)).
- The RMF2 document block set (`runic:p`, `runic:h`, `runic:ul`, `runic:ol`,
  `runic:li`) is open: a later minor may add blocks. Custom document or WPF
  markup factories must handle an unknown block name by failing or falling back;
  the built-in renderers fail closed
  ([#106](https://github.com/Runic-Artifex/runic-translations-sdk/pull/106)).
- `Rmf2MarkupContract.DeclaresMarkup(name)` reports whether a linked contract
  declares a markup name, such as a custom `shop:badge`, so an adapter can check
  its custom factories against the contract it was given (additive,
  [#113](https://github.com/Runic-Artifex/runic-translations-sdk/pull/113)).

| --- | --- |
| `Runic.Translations.CompiledRmf2*`, `Runic.Translations.TranslationsCompatibility` | `Runic.Translations.Generated.CompiledRmf2*`, `Runic.Translations.Generated.TranslationsCompatibility` (regenerate) |
| `CompiledTranslationDefinition.FromRmf2Inputs`, `CompiledTranslationLocale.CreateDeferred`/`ReadRmf2Values`, `TextArgument.CreateRmf2`, `TranslationPackContract.CreateRmf2V5`, `TranslationPackMessageContract.FromRmf2Inputs` | `GeneratedCatalogSupport.CreateDefinition`, `CreateDeferredLocale`/`ReadValues`, `CreateArgument`, `CreatePackContract`, `CreatePackMessageContract` |
| `TranslationsCompatibility.MessageGrammarVersion` | Removed (unused; the pack grammar is 5) |
| `new CompiledTextMessage(…)`, `new CompiledTextMessageNode(…)`, `new CompiledTextMessageVariant(…)`; `TextPatternFormatter`, `TextMessageSelector`, `TextRelativeTimeFormatter` | Internal; build v5 messages with `CompiledRmf2Message` and `CompiledTextMessage.FromRmf2` |
| `TranslationReference.CreateVersion1(…)` | Removed; write version 2 with the constructor (upgrade receivers first) |
| Generated ESM `createTextReference(key, inputs, { version: 1 })` | Removed (throws `RangeError`); write version 2 |
| `TranslationPackFailure.GetReason(packException)`, `GetRejectionId(e)`, `GetDiagnosticId(e)`, `TranslationPackFailure.DiagnosticId`, `RejectionIdPrefix` | `e.Reason`, `e.RejectionId`, `TranslationPackException.DiagnosticId`; `TranslationPackFailure.GetReason(Exception)` is unchanged |

| `options.MissingKey = …` after construction | `new TranslationOptions { MissingKey = … }` (init-only) |
| `diagnostic.Reason == "unknown-key"` | `diagnostic.Reason == TranslationReferenceDiagnosticReason.UnknownKey` (open enum, `Unknown = 0`) |
| A custom block factory that assumes the five built-in blocks | Handle an unknown block name: the block set is open |

### WPF

- `TranslationSource` takes the generated `IReadableMessages` instead of
  `object`, so passing `text` instead of `text.Messages` no longer compiles. It
  follows `ITranslationManager.SnapshotPublished` only, so a custom manager no
  longer needs `Invalidate()` after a refresh
  ([#109](https://github.com/Runic-Artifex/runic-translations-sdk/pull/109)).
- `WpfInlineRenderer` and `WpfDocumentRenderer` accept an already linked
  `Rmf2MarkupContract`, so an app with an inline and a document renderer links
  its catalog's contract once instead of once per renderer:
  `new WpfInlineRenderer(contract, navigate)` and
  `new WpfInlineRenderer(contract, navigate, new WpfInlineRendererOptions { Custom = …, Theme = … })`,
  with `WpfDocumentRendererOptions` for the document renderer. The constructors
  that take the contract JSON are unchanged and now link it once per renderer
  instead of parsing it twice (additive,
  [#113](https://github.com/Runic-Artifex/runic-translations-sdk/pull/113)).

| Before | After |
| --- | --- |
| `new TranslationSource(manager, (object)messages)`; `source.Messages` as `object` | `new TranslationSource(manager, text.Messages)`; `source.Messages` is `IReadableMessages` |
| Custom managers followed through `LocaleChanged` plus `Invalidate()` after a refresh | The source follows `SnapshotPublished` |

### Tooling

- `Runic.Translations.Tooling` is a stable package with no experimental API
  family. Its public API is the compiler (`TranslationCompiler` and its source,
  options, diagnostic and compilation types), XLIFF interchange with the review
  sidecar, artifact inspection and project scaffolding. The tool's command
  catalog, the workspace transactions, the MF2 syntax tree, the language service
  and the editor state are internal; the tool and the Translations Editor of the
  same commit use them, and they may be published later as additive API. The
  package no longer depends on Runic Command Line
  ([#107](https://github.com/Runic-Artifex/runic-translations-sdk/pull/107)).
- `TranslationDiagnosticSeverity` has an `Information` level and starts at
  `Information = 0`, so the numeric values of `Warning` and `Error` change. Tool
  JSON reports it as `info`
  ([#107](https://github.com/Runic-Artifex/runic-translations-sdk/pull/107)).
- Review states (`TranslationReviewState`, closed) and artifact kinds
  (`ArtifactKind`, open) are enums, project creation is asynchronous, compiler
  options use init properties, and XLIFF and MF2 document bytes are
  `ReadOnlyMemory<byte>`
  ([#107](https://github.com/Runic-Artifex/runic-translations-sdk/pull/107)).

| `Rmf2Workspace`, `Rmf2WorkspaceCache`, `Rmf2VariableReference`, `Rmf2ResourceWriter`, `TranslationWorkspaceTransaction`, `TranslationWorkspaceMutation`, the other `TranslationWorkspace*` types, `Translation*Request`, `TranslationKeyMutationKind`, `TranslationPendingTransaction` | Removed (internal) |

### Command-line tools

- `runic-translations` selects its output with `--format human|json`, like
  every Runic tool. `--runic-output` stays a hidden alias until 2.0; help and
  completions list only `--format`
  ([#104](https://github.com/Runic-Artifex/runic-translations-sdk/pull/104),
  [#112](https://github.com/Runic-Artifex/runic-translations-sdk/pull/112)).
- `runic-translations` uses the Runic exit codes: 0 success; 1 command failure,
  such as a `verify` difference or an I/O error; 2 invalid invocation or
  validation failure, including translation `RTR` diagnostics; 3 internal
  failure; 130 cancelled. `serve` reports the same codes
  ([#104](https://github.com/Runic-Artifex/runic-translations-sdk/pull/104)).
- A failed command reports the tool's own codes in the `runic.commandline/1`
  envelope instead of Runic Command Line's library codes: its fault is an `RTR`
  code and its diagnostics are in the tool's `RCLI82xx` block. Scripts that match
  these codes must switch; see the table and the
  [diagnostics guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.8.0/docs/guides/translations/diagnostics.md#rtr0087)
  ([#112](https://github.com/Runic-Artifex/runic-translations-sdk/pull/112)).
- New `runic-translations support preview|collect|remove --editor-diagnostics <zip> --destination <path>`
  builds, writes or removes the local support envelope from a Translations
  Editor diagnostic ZIP. It replaces `dotnet runic support --mode …` of Runic
  SDK, which forwards here. Its JSON payload is `runic.translations.support/1`,
  and its failures are `RTRSUP001`–`RTRSUP025` (formerly `RAPPSUP001`–`025`,
  same numbers and meanings)
  ([#104](https://github.com/Runic-Artifex/runic-translations-sdk/pull/104)).
- JSON schemas describe the `--format json` payloads
  (`runic.translations.tool/1`, `runic.translations.support/1`) and the `serve`
  protocol (`runic-translations-serve/1`); `runic-translations schema` also
  writes `translations-tool-v1`, `translations-support-v1` and
  `translations-serve-v1`. `output` and `error` in `runic.translations.tool/1`
  are display text: read `diagnostics` and `exitCode`. Later releases may add
  members. The `serve` protocol is a contract between the Vite plugin and the
  tool of the same release
  ([#111](https://github.com/Runic-Artifex/runic-translations-sdk/pull/111)).
- `runic-translations schema` no longer writes `editor-state-v1.schema.json`;
  the editor-state contract belongs to the Translations Editor
  ([#107](https://github.com/Runic-Artifex/runic-translations-sdk/pull/107)).
- `runic-translations lsp` is hidden from help. It still runs and, like the IDE
  extensions, is outside the 1.0 compatibility rules until the production
  language server
  ([#107](https://github.com/Runic-Artifex/runic-translations-sdk/pull/107)).
- `generate` and `verify` no longer accept the hidden `--emit-typescript`,
  `--emit-template-manifest` and `--emit-cpp` options, and `serve` no longer
  accepts those output groups. `init --class` is now `--class-name`, as in the
  templates
  ([#110](https://github.com/Runic-Artifex/runic-translations-sdk/pull/110)).
- `runic-translations` reads `@file` response files with Runic Command Line's
  opt-in `ResponseFiles()` instead of its own expander, with the same syntax:
  strict UTF-8 with an optional byte order mark, `#` comment lines, Windows
  quoting, nested files relative to their directory, at most 16 levels, and `@@`
  for a literal leading `@`. Help lists `@<file>`, and the shell completions
  complete a file name after `@`. An unusable response file now has its own code;
  see [Behaviour changes](#behaviour-changes)
  ([#114](https://github.com/Runic-Artifex/runic-translations-sdk/pull/114)).
- `runic-translations` writes the human output of its commands with Command
  Line outcome presenters (`CommandCatalogBuilder.PresentOutcome<T>`) instead of
  a custom outcome sink. The human output is unchanged, and the JSON envelopes
  keep their members and payloads
  ([#114](https://github.com/Runic-Artifex/runic-translations-sdk/pull/114)).

| Before | After |
| --- | --- |
| `--runic-output json` | `--format json` (the old spelling works until 2.0) |
| Exit 1 for translation diagnostics | Exit 2; 1 now means a command failure such as a `verify` difference or an I/O error |
| Exit 2 for an internal failure | Exit 3 |
| `dotnet runic support --mode preview\|collect\|remove …` | `runic-translations support preview\|collect\|remove …` |
| `RAPPSUP001`–`RAPPSUP025` | `RTRSUP001`–`RTRSUP025` |
| Support JSON `runic.application.tool/1` (text `Output`) | `runic.translations.support/1` with `mode`, `destination`, `digest`, `collectors`, `omissions`, `outboundTransportAttempts` |
| Fault `RCLI9000` | Fault `RTR0087`: the translations command could not be completed |
| `RCLI9014` | Fault `RTR0088` with `RCLI8214` diagnostics: `import-text` cannot import its input |
| `RCLI9001`, `RCLI9002`, `RCLI9003`, `RCLI9004`, `RCLI9005`, `RCLI9006` | `RCLI8201`, `RCLI8202`, `RCLI8203`, `RCLI8204`, `RCLI8205`, `RCLI8206` (same meanings) |

| `schema` writes 8 schemas, including `editor-state-v1` | 10: `editor-state-v1` is gone; `translations-tool-v1`, `translations-support-v1`, `translations-serve-v1` are new |

| Tool JSON `diagnostics[].severity` `error`/`warning` | Also `info` |

### Templates

- The hidden camelCase aliases `--defaultLocale`, `--className` and
  `--packageVersion` are removed; use `--default-locale`, `--class-name` and
  `--package-version`. The project template writes `RunicTranslationsEmitEsm`
  ([#110](https://github.com/Runic-Artifex/runic-translations-sdk/pull/110)).

### Runic Command Line 0.9.0

- `Runic.Translations.CommandLine` and `dotnet-runic-translations` are tested
  with Runic Command Line 0.9.0 and depend on its minor, `[0.9.0, 0.10)`. The
  former range was `>= 0.7.0-preview.1`. An application on an earlier Command
  Line must upgrade to 0.9.0 (see the Runic Command Line 0.8.0 and 0.9.0 release
  notes); a later Command Line minor needs a new Translations release
  ([#112](https://github.com/Runic-Artifex/runic-translations-sdk/pull/112),
  [#114](https://github.com/Runic-Artifex/runic-translations-sdk/pull/114)).
- The built-in English and German catalogs of `Runic.Translations.CommandLine`
  translate every Command Line 0.9.0 framework key, including the new
  `help.response-files` and `diagnostics.response-file-unreadable`,
  `-invalid-utf8`, `-unterminated-quote`, `-too-deep` and `-cycle`, and the
  earlier `help.json-payload-output-alias`
  ([#112](https://github.com/Runic-Artifex/runic-translations-sdk/pull/112),
  [#114](https://github.com/Runic-Artifex/runic-translations-sdk/pull/114)).

| Before | After |
| --- | --- |
| `Runic.Translations.CommandLine` → `Runic.CommandLine >= 0.7.0-preview.1` | `Runic.CommandLine [0.9.0, 0.10.0)` |

### Not planned for 1.0

Message references and terms with atomic fallback, document messages in XLIFF,
richer document blocks, per-locale structure overrides (`markup.structure` stays
reserved and rejected) and a web-hosted editor are not part of 1.0. See
[Not supported in 1.0](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.8.0/docs/guides/translations/rmf2.md#not-supported-in-10)
([#106](https://github.com/Runic-Artifex/runic-translations-sdk/pull/106)).

## Behaviour changes

- **Translation diagnostics exit with 2.** `runic-translations` exits with 2,
  not 1, for translation `RTR` diagnostics, `RTR0065` and `import-text`
  failures, and with 3, not 2, for an internal failure. An I/O or permission
  error is 1 and an invalid path argument is 2. `support` without a mode prints
  the group help and exits 0. Keep the tool and `Runic.Translations.Build` on
  the same release
  ([#104](https://github.com/Runic-Artifex/runic-translations-sdk/pull/104)).
- **The tool honours Runic Command Line's environment.**
  `RUNIC_COMMANDLINE_NO_INPUT=1` and option environment fallbacks now reach
  `runic-translations`; it used to build its own parse settings and ignore them.
  `--runic-output` parses exactly like `--format`, also before the command, and
  not after `--`
  ([#112](https://github.com/Runic-Artifex/runic-translations-sdk/pull/112)).
- **Response file failures are usage errors with their own codes.** A response
  file that cannot be used is reported by Runic Command Line, with its message
  and code, as a usage error (exit code 2): `RCLI1017` cannot be read,
  `RCLI1018` not valid UTF-8, `RCLI1019` unterminated quote, `RCLI1020` nested
  more than 16 levels, `RCLI1021` includes itself. A missing or unreadable
  response file was an I/O failure, `RCLI8205` with exit code 1; the other
  cases were `RCLI8203` with exit code 2 and the tool's own wording
  ([#114](https://github.com/Runic-Artifex/runic-translations-sdk/pull/114)).
- A host failure (`RCLI5000`) of a `support` command adds Runic Command Line's
  `RUNIC_COMMANDLINE_DEBUG` hint
  ([#114](https://github.com/Runic-Artifex/runic-translations-sdk/pull/114)).
- **Old MSBuild names fail the build** with `RTR0086` instead of being ignored
  ([#110](https://github.com/Runic-Artifex/runic-translations-sdk/pull/110)).
- **Transport writers emit version 2 only.** Generated ESM
  `createTextReference(…, { version: 1 })` throws a `RangeError`; readers still
  accept version 1
  ([#109](https://github.com/Runic-Artifex/runic-translations-sdk/pull/109)).

## Translations Editor

The Translations Editor is a separate product on its own timeline and is not
distributed with this release; these notes cover builds from source at
`v0.8.0`. See the
[editor README](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.8.0/apps/translations-editor/README.md).

- The editor is built on Runic SDK 0.10.0: `Runic.Application.Views` and its
  ReactiveUI adapter, `Runic.Application.Views.CsWebUi` 0.10.0-preview.1 with
  `CsWebUi` 2.5.0-beta.4.7, and the npm packages `@runic-artifex/views`,
  `@runic-artifex/svelte` and `@runic-artifex/sveltekit` 0.10.0. It used
  0.7.0-preview.6 under the former package names (`Runic.Application.CsWebUi`,
  `Runic.Application.ReactiveUI`). The page and the host speak Views protocol 3
  ([#115](https://github.com/Runic-Artifex/runic-translations-sdk/pull/115)).
- The editor opens its window through `RunicCsWebUiHost` and `RunicWindow<T>`;
  `--webview`, `serve` and `--native-shell-canary` keep their behaviour. `edit`
  also honours Runic's serve-only switch: with `RUNIC_APPLICATION_SERVE_ONLY=1`
  it starts its local server, writes `RUNIC_APPLICATION_URL=<url>` and serves
  until a line is read from standard input, without opening a browser. The
  packaged page loads the host-neutral `runic-views.js`, which the CS-WebUI host
  package copies to `www/` with the built frontend
  ([#115](https://github.com/Runic-Artifex/runic-translations-sdk/pull/115)).
- The first save of a newly loaded document no longer fails with "The selected
  document route is unavailable" when the command's reply reaches the page
  before the snapshot that lists the document
  ([#115](https://github.com/Runic-Artifex/runic-translations-sdk/pull/115)).
- The editor runs on Runic Command Line 0.9.0. It selects its output with
  `--format human|json`; `--runic-output` is a hidden alias. Its exit codes
  follow the Runic tool table, and it writes its human output with Command Line
  outcome presenters
  ([#112](https://github.com/Runic-Artifex/runic-translations-sdk/pull/112),
  [#114](https://github.com/Runic-Artifex/runic-translations-sdk/pull/114)).
- The editor state (`runic.translations.editor-state/1`) and its schema belong
  to the editor and are not an SDK contract. The
  `runic.translations.editor-diagnostics/1` bundle is covered only as input of
  `runic-translations support`
  ([#106](https://github.com/Runic-Artifex/runic-translations-sdk/pull/106),
  [#107](https://github.com/Runic-Artifex/runic-translations-sdk/pull/107)).

| Before | After |
| --- | --- |
| `export`/`report`/`import --format xliff\|review` | `--interchange xliff\|review`; `--format xliff` fails with `RCLI1010` and exit 2 |
| `--runic-output json` | `--format json` |
| Validation failure (workspace diagnostics, refused or failed report/import/export, smoke-test failure): exit 1 | Exit 2 |
| Unavailable (packaged web UI missing, native shell canary): exit 2 | Exit 1 |
| Host or internal failure: exit 2 | Exit 3 |
| Cancelled: exit 1 | Exit 130 |
| `runic.editor.command/1` payload in PascalCase | camelCase (`summary`, `xliffExport`, `reviewExport`, `xliffImport`, `reviewImport`, `applied`, `diagnostics`) |
| Workspace diagnostic code `RCLI9050` in `validate --format json` | `RCLI8050` |
| `WEBUI_BROWSER_PATH` | `CSWEBUI_BROWSER_PATH` (the `nix develop .#editor` shell sets both) |

### Behaviour changes

- `edit` picks its browser from `CSWEBUI_BROWSER_PATH`, which CS-WebUI uses
  without fallback; it no longer reads `WEBUI_BROWSER_PATH`
  ([#115](https://github.com/Runic-Artifex/runic-translations-sdk/pull/115)).
- When no browser or WebView can be shown, `edit` writes the reason (such as
  `window-show-failed` or `browser-not-found`) to standard error and fails with
  `REDIT0009`, exit code 1, instead of an internal failure with WebUI's
  exception
  ([#115](https://github.com/Runic-Artifex/runic-translations-sdk/pull/115)).
- The editor's JSON envelope carries the invocation's own `requestId`, as
  `runic-translations` and every other Runic tool do. It was always
  `runic-translations-editor`
  ([#114](https://github.com/Runic-Artifex/runic-translations-sdk/pull/114)).

## IDE extensions

The VS Code and Visual Studio extensions are attached to the GitHub release as
`runic-translations.vsix` and `runic-translations-visualstudio.vsix`; they are
not published to an extension marketplace
([#106](https://github.com/Runic-Artifex/runic-translations-sdk/pull/106)).

- They are versioned from the release version: Visual Studio `0.8.0.1000`,
  VS Code `0.8.1000`. As a plain release, the VS Code VSIX is no longer marked
  pre-release.
- They are a preview product until the production language server (2.0) and
  carry the "Preview" label on every release. Like the hidden `lsp` command they
  use, their commands and settings are outside the 1.0 compatibility rules and
  may change in a minor release.
- From 1.0, `1.0.0-rc.N` releases map to Visual Studio `1.0.0.(500 + N)` and
  VS Code `1.0.(500 + N)`, marked pre-release, and `-preview.N` is limited to
  N from 1 to 499, so every preview sorts below every release candidate.

| Before | After |
| --- | --- |
| `0.7.0-preview.4`: Visual Studio `0.7.0.4`, VS Code `0.7.4` (pre-release) | `0.8.0`: Visual Studio `0.8.0.1000`, VS Code `0.8.1000` (not pre-release, "Preview" label) |
| VS Code VSIX of a final release without the "Preview" label | Every VSIX carries the "Preview" label |

## Security

These come from the October 2026 dependency exposure check. None needs action
beyond upgrading.

- **Vite.** Vite 8.3.0–8.3.2 is affected by six advisories, all fixed in 8.3.3:
  [GHSA-587h-7wmj-h5pm](https://github.com/advisories/GHSA-587h-7wmj-h5pm)
  (high: launch-editor existence-check bypass on Windows),
  [GHSA-698v-4r3x-3vcv](https://github.com/advisories/GHSA-698v-4r3x-3vcv),
  [GHSA-r825-w8mm-5pxw](https://github.com/advisories/GHSA-r825-w8mm-5pxw),
  [GHSA-9jrq-w75r-8gcw](https://github.com/advisories/GHSA-9jrq-w75r-8gcw),
  [GHSA-rq7h-c2jc-7f22](https://github.com/advisories/GHSA-rq7h-c2jc-7f22) and
  [GHSA-vfpm-58rq-9qcg](https://github.com/advisories/GHSA-vfpm-58rq-9qcg).
  They affect the development server only. The Vite plugin requires Vite 8.3.3
  or later, and the Svelte and SvelteKit packages, the editor frontend and the
  quick starts are built and tested with 8.3.4
  ([#105](https://github.com/Runic-Artifex/runic-translations-sdk/pull/105),
  [#108](https://github.com/Runic-Artifex/runic-translations-sdk/pull/108)).
- **MessagePack.** The Visual Studio extension builds against MessagePack
  2.5.303 instead of 2.5.192, which was affected by
  [CVE-2026-92707 / GHSA-qhrr-8q5h-9q3h](https://github.com/advisories/GHSA-qhrr-8q5h-9q3h)
  (denial of service through nested arrays). Visual Studio supplies MessagePack
  at run time and the VSIX ships only `Runic.Translations.VisualStudio.dll`, so
  this cleans up the build graph and the audit
  ([#105](https://github.com/Runic-Artifex/runic-translations-sdk/pull/105)).
