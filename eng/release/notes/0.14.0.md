# Runic Translations 0.14.0

Install matching `0.14.0` packages from NuGet and npm: the eight NuGet packages
(`Runic.Translations`, `.Build`, `.CommandLine`, `.Hosting`, `.Tooling`, `.Wpf`,
`.Templates` and the `dotnet-runic-translations` tool) and the three npm
packages (`@runic-artifex/vite-plugin-runic-translations`,
`@runic-artifex/translations-svelte` and `@runic-artifex/translations-sveltekit`).

0.14.0 is released on its own, without a release train.
**`Runic.Translations.CommandLine` 0.14.0 needs Runic Command Line 0.13**, as
0.13.0 did.

This release brings the language server's refactorings to every LSP editor and
makes Translations much smaller in a NativeAOT executable. It also fixes paths
on Windows, keeps pseudo-locales out of locale fallback, and lets the
Translations Editor publish for Windows and macOS from any machine.

Until 1.0 a new minor may contain breaking changes. See
[Upgrading from 0.13](#upgrading-from-013) and
[Versions before 1.0](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.14.0/eng/release/README.md#versions-before-10).

## Highlights

- **Refactorings in every LSP editor.** With `"runicProtocol": 2` in its
  `initializationOptions`, a client gets F2 rename of MF2 inputs, slots and
  resources, Extract Group and Inline Resource as code actions, and command
  edits the server applies itself, without client code of their own: in Neovim,
  Helix, JetBrains IDEs with LSP4IJ and Visual Studio 2026's LSP client. Without
  the opt-in the server behaves as in 0.13
  ([details](#refactorings-through-standard-lsp-in-the-language-server-204)).
- **Smaller NativeAOT executables.** On linux-x64 a console application with
  the editor's catalog (872 messages in English and German) shrinks from
  4.39 MB to 3.17 MB: Hot Reload no longer links reflection, locale data is
  compressed, and a message adds about 200 bytes instead of 550. The markup
  contract is compressed too, and overlays are linked only when the
  application creates one
  ([details](#smaller-nativeaot-executables-216-217-218)).
- **CLDR data as data, and an opt-in subset.** The CLDR locale tables and
  plural rules are compact data instead of code, about 80 KB less in a NativeAOT
  executable. `<RunicTranslationsCldrSubset>true</RunicTranslationsCldrSubset>`
  embeds only the CLDR data of the catalog's languages instead of the full 52 KB
  ([details](#smaller-cldr-data-in-nativeaot-executables-219)).
- **Fixes.** A pseudo-locale is chosen only by its own tag, so a Debug build no
  longer formats `en-XA` text for `en-US` (#212). On Windows the Vite plugin
  updates an edited message in place again (#210), and the tools attribute each
  resource file to the right one of several `sourceRoots`. The Translations
  Editor publishes for Windows and macOS from Linux, without its smoke test
  ([details](#fixes)).

## Refactorings through standard LSP in the language server (#204)

`runic-translations lsp` now offers its refactorings through the standard
LSP features every editor has, after a client opts in to the Runic protocol
revision 2 with `initializationOptions.runicProtocol: 2`
([#205](https://github.com/Runic-Artifex/runic-translations-sdk/pull/205),
[#206](https://github.com/Runic-Artifex/runic-translations-sdk/pull/206)):

- **F2** renames MF2 caller inputs and slot references in every locale's
  resource, as well as resources and locals, with `prepareRename` showing the
  current name. In a workspace with application sources, a resource rename asks
  whether to rename in resource sources only, instead of refusing; Runic still
  does not update call sites.
- **Extract Group** and **Inline Resource** are `refactor.extract` and
  `refactor.inline` code actions: "Extract group 'shop' to shop/en.rmf2" on a
  group's name, and one "Inline into ../en.rmf2" per ancestor resource of the
  same locale.
- The `runic.*` refactoring commands apply their edits through
  `workspace/applyEdit`.
- The server registers its file watchers with clients that support it, reports
  its version in `serverInfo`, and answers unknown requests with `MethodNotFound`
  and failed ones with `RequestFailed`.

So Neovim, Helix, JetBrains IDEs with LSP4IJ and the next Visual Studio
extension get the refactorings without client code of their own. The
[language server guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.14.0/docs/guides/translations/language-server.md#protocol-revisions)
lists protocol 2 and has setups for these editors. Without the opt-in the server
behaves as in 0.13, so editor extensions from runic-editors 0.21 keep working;
0.15 is planned to remove that behaviour.

## Smaller NativeAOT executables (#216, #217, #218)

Translations adds much less to a trimmed or NativeAOT executable. On linux-x64, the editor's catalog (872 messages in
English and German) in a console application shrinks from 4.39 MB to 3.17 MB:

- **Hot Reload no longer links reflection** (#216). The Hot Reload check (`MetadataUpdater.IsSupported`) is now a
  constant in a trimmed publish, so the trimmer removes the catalog tracking and the reflection it used: about 350 KB.
  A Debug build and `dotnet watch` still apply edited catalog text in place, as before. The runtime's argument checks
  no longer call `Enum.IsDefined`.
- **Locale data is compressed** (#217). A generated catalog embeds each locale's messages as DEFLATE data, about a
  tenth of the size (the editor's catalog: 505 KB to 37 KB), and inflates a locale once, on its first use. On the
  editor's 256 KB English locale this adds about 0.8 ms and a transient 300 KB buffer to the first access.
- **Messages are data, not code** (#218). A generated catalog describes its messages' keys and inputs in one message
  table that the runtime reads in a loop, and each accessor calls one shared formatting body. A message adds about
  200 bytes to the executable instead of 550 (the editor's catalog: 389 KB less). On the editor's catalog the first
  provider and the first key access take about 0.1 ms longer together.

`tests/aot-size` measures a NativeAOT probe with a generated catalog, and CI checks its size budgets.

## Smaller CLDR data in NativeAOT executables (#219)

- **CLDR tables and plural rules are data** (D072.2). The runtime's pinned CLDR locale tables and plural rules were
  compiled to about 70 KB of code. They are now compact data that the runtime decodes on first use, and plural rules
  are interpreted from bytecode. The results are identical for every CLDR locale and plural category. A NativeAOT
  executable shrinks by about 80 KB. The first use costs about 50 µs more once, and a plural selection about 45 ns.
- **Opt in to your catalog's CLDR data only** (D072.6). Set `<RunicTranslationsCldrSubset>true</RunicTranslationsCldrSubset>`
  in an application that never adds a locale of another language at run time. The build then embeds only the CLDR
  number, date, list and relative-time data of the catalog's languages, and a trimmed or NativeAOT publish drops the
  full 52 KB. A locale outside the subset, such as one a pack adds, formats as a locale without CLDR data, with lists
  and relative times in CLDR root's language-neutral patterns (`a, b, c`, `-1 d`). It is reported once (`Runic-Translations` event 4).
  `RunicTranslationsCldrLocale` items add locales. The default is unchanged. See the `Runic.Translations.Build` README.

## Upgrading from 0.13

Update every Runic Translations package, NuGet and npm, to 0.14.0 together.
Runic Command Line stays at 0.13.

- **Generated catalogs need the 0.14 runtime.** C# that `Runic.Translations.Build`
  0.14 generates against `Runic.Translations` 0.14 requires RMF2 runtime ABI 4,
  and fails with `NotSupportedException` on an earlier runtime: reference both
  packages at the same version. The 0.14 runtime still runs the ABI 3 code that
  0.13 generated, so libraries packed with 0.13 keep working on it
  ([details](#behaviour-and-output-changes)).
- **Libraries packed with `Runic.Translations.Build` 0.13** depend on
  `Runic.Translations` `[0.13.0, 0.14.0-0.0)`, so an application on the 0.14.0
  runtime gets NuGet warning `NU1608`. Pack a library update with 0.14.0, as for
  every Runic Translations minor (see
  [Versions](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.14.0/docs/guides/translations/libraries.md#versions)).
- **Language server clients opt in to protocol 2.** A client that sends
  `"runicProtocol": 2` in `initializationOptions` gets the standard rename and
  code actions; one that doesn't, such as the editor extensions from
  runic-editors 0.21, gets the 0.13 behaviour. 0.15 is planned to remove it, so
  move custom clients to protocol 2 during 0.14
  ([language server guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.14.0/docs/guides/translations/language-server.md#protocol-revisions)).
- **Deprecated: framework text from your own catalog in Runic.Translations.CommandLine.**
  A message in your application's catalog named after a `runic-command-line`
  key, such as `help { usage = Synopsis }`, still overrides that command-line
  text in 0.14, but the build now reports it as warning `RTR0107`, and
  `TranslationCommandTextResolver` writes a trace warning once when it uses
  one. Runic Translations 0.15 removes this second override path: the resolver
  then asks your catalog only for your own keys (`DescriptionKey` text), and
  the framework text returns. To migrate, move each such message, unchanged,
  to `translations/overrides/runic-command-line/<locale>.rmf2`, add
  `{ "catalog": "runic-command-line", "from": "Runic.Translations.CommandLine" }`
  to `overrides` in `runic.json`, and register `AppTextCatalog.Overlays` with a
  context-based resolver (`new TranslationCommandTextResolver(context, AppTextCatalog.CatalogId)`,
  the `TranslationContextBuilder` constructor, or `AddRunicCommandLineTranslations()`);
  the snapshot and manager constructors ignore overlays. The build then checks
  each override against the framework catalog (`RTR0103`). See
  [Framework text](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.14.0/docs/guides/translations/framework-text.md#the-second-path-for-command-line-text-deprecated).

### Behaviour and output changes

- Generated C# requires RMF2 runtime ABI 4 (`TranslationsCompatibility.Rmf2RuntimeAbiVersion` is 4) when the
  referenced `Runic.Translations` runs it, because it embeds locale data as DEFLATE data
  (`GeneratedCatalogSupport.ReadDeflatedValues`). With a `Runic.Translations` before 0.14 the generator still emits
  the JSON with ABI 3, and the 0.14 runtime still runs code generated for ABI 3. A catalog compiled against 0.14 and
  run with an earlier `Runic.Translations` fails with `NotSupportedException`; use the same version of
  `Runic.Translations` and `Runic.Translations.Build`. ESM output and external packs are unchanged (#217).
- RMF2 runtime ABI 4 generated C# also reads its message definitions, keys and external-pack contracts from one
  message table (`<Class>CatalogData.MessageTable`, `GeneratedCatalogSupport.ReadDefinitions`, `CreateKeys`,
  `CreatePackContract`), and its accessors call shared `__Format`/`__FormatContent` bodies with the typed
  `GeneratedCatalogSupport.CreateArgument` overloads. The generated API and the formatted text are unchanged; with a
  `Runic.Translations` before 0.14 the generator still writes ABI 3 code per message (#218).
- With RMF2 runtime ABI 4, `XCatalog.Rmf2MarkupContract` returns the same JSON, inflated on each read from DEFLATE
  data in `XCatalogData` (`GeneratedCatalogSupport.ReadDeflatedText`) instead of a string literal. A translation
  context links the overlay composition only when the application creates a `TranslationOverlay`
  ([runic-sdk#1109](https://github.com/Runic-Artifex/runic-sdk/issues/1109)).

### Experimental features and how to opt in

- **Language server protocol 2** (#204): send `"runicProtocol": 2` in the
  language server's `initializationOptions` for standard rename, refactor code
  actions and server-applied command edits. The `lsp` command and its protocol
  stay outside the 1.0 compatibility rules for now
  ([details](#refactorings-through-standard-lsp-in-the-language-server-204)).
- **Language server protocol 2 in Visual Studio 2026** (#208): the server no
  longer requires capabilities that Visual Studio 2026's LSP client does not
  advertise but supports. A mixed-workspace resource rename always asks with
  `window/showMessageRequest`. Refactor actions are resolved for any client with
  `codeAction.resolveSupport`, and carry their edit for clients without it. A
  client that cannot register file watchers gets the server's own. Without the
  `delete` resource operation, Inline Resource empties the inlined file instead
  of deleting it
  ([client compatibility](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.14.0/docs/guides/translations/language-server.md#client-compatibility)).

## Fixes

- A development build with `pseudoLocales` no longer resolves an ordinary locale to a pseudo-locale. A pseudo-locale
  (`en-XA`, `ar-XB`) is now chosen only when it is requested by its own tag; locale fallback and negotiation of every
  other tag skip it in .NET (`SetLocaleAsync`, `LocaleNegotiation`, `SetLocaleFromPreferencesAsync`, overlay-added
  locales) and in ESM (`resolveLocale`, `negotiateLocale`, the SvelteKit locale routing). A catalog with `"baseLocale":
  "de"` and `"locales": ["de"]` kept German for `SetLocaleAsync("en-US")` in a Release build but formatted `en-XA`
  pseudo text in a Debug build; both now keep German (#212).
- On Windows, `@runic-artifex/vite-plugin-runic-translations` updates an edited message in place again, and reloads the
  page when the catalog's structure changed. The plugin looked the regenerated modules up in Vite's module graph by their
  native `\` paths, which matched nothing, so the page kept the old text until a manual reload. Every path it passes to
  Vite's module graph and watcher now has Vite's form (`normalizePath`), for the application's catalog and the dependency
  catalogs alike (#210).
- On Windows, a project with several `sourceRoots` attributes each resource file to its own source root again. The
  language server's hover, completion and rename keys, its refactorings and the authoring edits used the first root's
  namespace for files in a sibling root, and did not reject files outside every root. Every containment check of the
  tools now handles both separators, other drives and shares, and the platform's case rules.
- On Windows, `runic-translations` export, import and message edits print a path outside the working directory in full with
  `/`, as on Linux and macOS, instead of a relative `..\` path.
- The Translations Editor publishes for Windows and macOS from any build machine. `dotnet publish -r win-x64` or
  `-r osx-arm64` on Linux failed with CS0234: the Views bootstrap build clears the runtime identifier, so it chose the
  build machine's platform package, which the restore for the target runtime does not contain. The bootstrap now compiles
  without a platform package, and the Windows and macOS builds compile cleanly with warnings as errors.
- A published Translations Editor no longer carries its smoke test and the Runic SDK's window test host
  (`Runic.Application.Testing`, `Microsoft.Extensions.TimeProvider.Testing`): a framework-dependent linux-x64 publish is
  735,577 bytes smaller and the NativeAOT executable 410,704 bytes. Verification builds (`bun run build`,
  `bun run verify-editor-packed`) compile the smoke test with `-p:RunicEditorSmokeTest=true` and run the same scenarios;
  in other builds `--smoke-test` fails with `REDIT0001`.

## Release engineering

- npm archives are reproducible: a package's `gitHead` is now the commit that last
  changed its inputs (its directory, the workspace packages it depends on and the
  shared build files), not the commit the build ran on, so a commit elsewhere leaves
  the archive and its integrity unchanged. npm's provenance still names the release
  commit. The release check accepts such a `gitHead` when it is an ancestor of the
  release commit with the same inputs (`eng/release/README.md`, "npm archive source commit").
- `@sveltejs/kit` is updated to 3.1.1 and `@sveltejs/adapter-node` (in
  `examples/component-library/web`) to 6.0.1, which fix GHSA-mw6w-2fmv-pvw3 and
  GHSA-rqw3-x7hx-mm3p.
- Publish preview's train gate (row P-tr) takes runic-sdk's newest successful
  `main` run at or after a pinned commit (`sdk: run@<commit>`), never simply the
  newest run, and refuses to publish if Translations `main` moved since the commit
  that runic-sdk's train feed served.
