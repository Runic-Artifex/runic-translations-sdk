## Refactorings through standard LSP in the language server (#204)

`runic-translations lsp` now offers its refactorings through the standard
LSP features every editor has, after a client opts in to the Runic protocol
revision 2 with `initializationOptions.runicProtocol: 2`
([#205](https://github.com/Runic-Artifex/runic-translations-sdk/pull/205),
[#206](https://github.com/Runic-Artifex/runic-translations-sdk/pull/206)):

- **F2** renames MF2 caller inputs and slot references in every locale's
  resource, as well as resources and locals, with `prepareRename` showing the
  current name. In a workspace with application sources, a resource rename asks
  whether to rename in resource sources only, instead of refusing; Runic still
  does not update call sites.
- **Extract Group** and **Inline Resource** are `refactor.extract` and
  `refactor.inline` code actions: "Extract group 'shop' to shop/en.rmf2" on a
  group's name, and one "Inline into ../en.rmf2" per ancestor resource of the
  same locale.
- The `runic.*` refactoring commands apply their edits through
  `workspace/applyEdit`.
- The server registers its file watchers with clients that support it, reports
  its version in `serverInfo`, and answers unknown requests with `MethodNotFound`
  and failed ones with `RequestFailed`.

So Neovim, Helix, JetBrains IDEs with LSP4IJ and the next Visual Studio
extension get the refactorings without client code of their own. The
[language server guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.14.0/docs/guides/translations/language-server.md#protocol-revisions)
lists protocol 2 and has setups for these editors. Without the opt-in the server
behaves as in 0.13, so editor extensions from runic-editors 0.21 keep working;
0.15 is planned to remove that behaviour.
