# Runic Translations 0.6.0-preview.6

## Build-time XAML checks

- A file can now opt out of the XAML checks with item metadata, for example
  `<Page Update="Views/OrderSummary.xaml" TranslationsValidateXaml="false" />`
  (also honoured on `ApplicationDefinition` and `TranslationXaml` items). Use it
  for a file whose `TranslationProperties.Source` is inherited at run time from
  another file, an `App.xaml` style or code-behind; previously such a file was
  checked against `TranslationsXamlCatalog` and could fail with `RTR0081`.
- Design-time content is no longer checked: attributes and elements in
  `mc:Ignorable` namespaces (such as `d:`) and everything inside
  `mc:AlternateContent` are skipped.
- With a runtime that lacks the readable surface, XAML is not checked; the single
  `RTR0068` warning replaces one `RTR0081` error per static key.
- Editing a XAML file revalidates only that file. The catalog is no longer
  relinked and C# sources are no longer regenerated on each XAML change.
- `TranslationsXamlCatalog`, and per-file `TranslationXaml Catalog` assertions,
  can name the catalog of a directly referenced project, so XAML in a WPF
  application is checked against translations that live in a class library.
  Disable this with `TranslationsXamlReferencedCatalogs=false`.

## XAML argument order and explicit sources

- New warning `RTR0084`: `{rt:Message}` with `Arg0`..`Arg3` for a message with
  two or more inputs. Positions follow the generated parameters, which are
  sorted by input name rather than by their order in the text, so
  `Arg0={Binding Name}, Arg1={Binding Email}` for `Editing {$name} ({$email})`
  bound the values swapped without a diagnostic. The warning shows the mapping
  (`Arg0=email, Arg1=name`); use named `MessageInput` entries instead. Projects
  that treat warnings as errors and bind several inputs by position need to
  switch to the named form or suppress `RTR0084`.
- An explicit source no longer disables the default-catalog checks for the
  whole file. A `Source=` on a `Message` excludes only that message; an
  attached `rt:TranslationProperties.Source` excludes its element's content and
  the file's templates, styles and resources; only a `Setter` for it still
  excludes the whole file. Keys that are skipped are reported once per source
  as the informational `RTR0085`, with the line and the remedy. Typos elsewhere
  in such a file are now reported as `RTR0081`.
- `RTR0081` suggests the closest readable key. `RTR0082` names the specific
  problem (gap, mixed forms, duplicate, unknown or missing name, wrong count),
  lists the positional mapping and no longer prints "requires 0 input(s): .".
  `RTR0083` names the adapter to use.

## Runtime, generated catalogs and WPF

- Generated catalogs gain `CreateManager(...)`, a synchronous factory for
  embedded catalogs. Use it in startup code that cannot await, such as WPF
  applications with `StartupUri`; the `Runic.Translations.Wpf` docs include
  `StartupUri` guidance.
- `ITranslationSnapshot.TryGetKey` and `TryGetPlaceholders` find messages by
  name (`help.usage` or `help_usage`) and describe their inputs.
- `Runic.Translations.Wpf` defines the XAML namespace
  `https://runic-artifex.eu/xaml/translations` (prefix `rt`). The CLR namespace
  form keeps working.
- Runtime plumbing used by generated catalogs (`CompiledRmf2*`,
  `TranslationsCompatibility`, `CompiledTextMessage.Rmf2V5`,
  `TranslationPackContract.CreateRmf2V5`, `TextArgument.CreateRmf2`,
  `TextArgumentFormat.Fixed0..6`/`Percent0..4` and the legacy formatter
  primitives) is hidden from IntelliSense with `[EditorBrowsable(Never)]`, as
  are generated hex-encoded members when readable members exist. The API itself
  is unchanged.

## Runic.CommandLine text

- The new `Runic.Translations.CommandLine` package's
  `TranslationCommandTextResolver` translates Runic.CommandLine help,
  diagnostics and faults out of the box with built-in English and German
  catalogs. Your own catalog can override any key, with no hand-written key
  mapping. See the
  [Command Line guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.6.0-preview.6/docs/guides/translations/command-line.md).

## Tool

- `validate`, `generate` and `verify` default `--project` to `./runic.json`,
  then `./translations/runic.json`.
- Help is one aligned, described help system, also printed on usage errors.
  `generate` and `verify` help no longer lists `--emit-typescript`,
  `--emit-template-manifest` and `--emit-cpp`. They have no renderer and still
  fail with `RTR0065` when requested.
- In JSON mode, translation diagnostics are native RTR entries with locations
  and help links: in `payload.diagnostics` on success and in `fault.data`
  (`runic.translations.tool/1`) on failure. They are no longer `RCLI9012`
  strings, and the payload properties are camelCase (`output`, `error`,
  `diagnostics`). `serve` responses include the same RTR fields.
- The tool uses Runic.CommandLine 0.6.0-preview.3.
- The tooling API adds `TranslationsToolDiagnostic` and
  `TranslationsToolCommandResult.Diagnostics`; the `project` parameter of
  `Validate`, `Generate` and `Verify` is optional.

## Templates

- `runic-translations-project` and `runic-translations` use kebab-case options:
  `--default-locale`, `--class-name`, `--package-version`, `--locales`,
  `--emit-esm`. The camelCase names of earlier previews still work as hidden
  aliases.
- The generated namespace follows `--name`, and `--locales de,fr` declares extra
  locales.
- The project template no longer emits ESM by default; pass `--emit-esm` when a
  web front end consumes the project's ESM output through the Vite plugin's
  manifest mode.

## Diagnostics and documentation

- In a build, each translation diagnostic appears once, with its help link.
  There is no `RCLI9012` prefix and no `MSB3073`. A failed JSON/ESM generation
  in a C# project is reported by the compilation.
- `RTR0011` names the dotted message path and suggests the closest base-locale
  key. `RTR0010` names the path and points at the locale's file. A message that
  fails to compile no longer also reports `RTR0010` or `RTR0011`.
- `RTR` diagnostics link to their entry in the
  [diagnostics reference](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.6.0-preview.6/docs/guides/translations/diagnostics.md)
  at your release. The reference now covers `RTR0020`, `RTR0023` and the
  `runic-translations` tool's `RCLI9xxx` codes.
- Package READMEs on nuget.org and npm link to the documentation of the release
  you installed instead of the `main` branch.
- The .NET, SvelteKit and Vite quick starts have Troubleshooting sections for
  `CS8032`, `AsyncLocalStorage`/`nodejs_compat` and manifest mode.

## Upgrading

- Scripts that read `dotnet-runic-translations` JSON output read diagnostics as
  RTR entries in `payload.diagnostics` or `fault.data` instead of `RCLI9012`
  strings, and camelCase payload properties (`output`, `error`,
  `diagnostics`).
- Projects created from `runic-translations-project` whose web front end uses
  the Vite plugin's manifest mode pass `--emit-esm`.
- Projects that treat warnings as errors and bind several `{rt:Message}` inputs
  by position switch to named `MessageInput` entries or suppress `RTR0084`.
