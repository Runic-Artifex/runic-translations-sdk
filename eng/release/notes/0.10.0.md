# Runic Translations 0.10.0

Install matching `0.10.0` packages from NuGet and npm: the eight NuGet packages
(`Runic.Translations`, `.Build`, `.CommandLine`, `.Hosting`, `.Tooling`, `.Wpf`,
`.Templates` and the `dotnet-runic-translations` tool) and the three npm
packages (`@runic-artifex/vite-plugin-runic-translations`,
`@runic-artifex/translations-svelte` and `@runic-artifex/translations-sveltekit`).

0.10.0 is the Translations release of the 0.18 release train: Runic Command Line
0.12.0, then Runic Translations 0.10.0, then Runic SDK 0.18.0. The three were
restored, built and run together with warnings as errors before any of them was
published. **`Runic.Translations.CommandLine` 0.10.0 needs Runic Command Line
0.12**, and Runic SDK 0.18's `Runic.Application.Views.Translations` needs
Runic Translations 0.10.

Until 1.0 a new minor may contain breaking changes; this release has the ones in
[Upgrading from 0.9](#upgrading-from-09). See
[Versions before 1.0](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.10.0/eng/release/README.md#versions-before-10).

## German command-line text for Runic Command Line 0.12 (#168)

`Runic.Translations.CommandLine` 0.9.1 required Runic Command Line
`[0.9.1, 0.10.0)`. With Command Line 0.10 or 0.11, restore reported `NU1608`
(an error with warnings as errors, also in test projects), and the usage hint
that Command Line 0.10 added ("Run "tool greet --help" for more information.")
stayed English. 0.10.0 fixes both:

- **Lockstep with Command Line.** The adapter supports exactly one Command Line
  minor, now 0.12: it depends on `Runic.CommandLine` `[0.12.0, 0.13.0-0.0)`.
  Every Command Line minor is followed in the same train by a Translations
  release for it, and patches add no keys. Both the adapter's README and this
  repository's README carry the version table.

  | Runic.Translations.CommandLine | Runic.CommandLine |
  | --- | --- |
  | 0.10.x | 0.12.x |
  | 0.9.x | 0.9.x |

- **The text comes from Command Line.** Runic Command Line 0.12 packs the
  `runic-command-line` catalog sources (`runic.json`, `en.rmf2`, `de.rmf2`) and
  its key list `text-keys.json` under `translations/`, and its own CI checks
  that every key has English and German. The adapter compiles exactly the text
  of the Command Line release it is built against and reads each key's
  argument names from that release's `CommandTextKeys`, so a key and its German
  cannot drift apart. Its own copy of the text and of the argument table is
  gone.
- **Every Command Line 0.12 key** has English and German, including the usage
  hint (`hints.usage`), the help link (`hints.help-link`), the redaction notes
  (`redaction.*`), the empty command line (`diagnostics.missing-command`), the
  exit-codes heading (`help.exit-codes`) and the process faults
  (`faults.RCLI6001` to `faults.RCLI6011`). `faults.RCLI4001` keeps the more
  specific `diagnostics.prompt-*` text, as before. A test compares the compiled
  catalog with `text-keys.json`, key for key.
- **German wording follows Command Line 0.12.** The usage errors name what they
  are about, for example `Die Option '--bogus' ist unbekannt.` instead of
  `Unbekannte Option. (--bogus)`. Since Command Line 0.10 a usage error in human
  output has no `RCLI` code prefix (`--format json` carries it) and ends with the
  usage line and the hint:

  ```text
  Die Option '--unknown' ist unbekannt.
  Aufruf: localized greet <name> [Optionen]
  Weitere Informationen erhalten Sie mit "localized greet --help".
  ```

- **`AddRunicCommandLineTranslations(applicationCatalogId)`** (new, in
  `Runic.Translations.CommandLine` through `Runic.Translations.Hosting`) adds
  `runic-command-line` to the application's shared context and registers an
  `ICommandTextResolver` over it, so one `SetLocaleAsync` switches the
  application's text and the command line's together, with the context's
  overrides applied. The adapter package now depends on
  `Runic.Translations.Hosting` and, through it, on
  `Microsoft.Extensions.DependencyInjection.Abstractions`.
- **A locale the framework text lacks is reported.** When the application's text
  has the requested language and `runic-command-line` does not, the resolver
  writes one `warning:` line to standard error and a trace warning, as
  `runic-views` logs event 1261. An override file
  (`translations/overrides/runic-command-line/<locale>.rmf2`) adds the locale.
- **Lead with a context.** The READMEs now lead with
  `new TranslationCommandTextResolver(context, AppTextCatalog.CatalogId)`. The
  snapshot and manager constructors use the built-in text without the
  context's overlays, so a build-time override of `runic-command-line` is
  ignored there; they are unchanged.

[Framework text](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.10.0/docs/guides/translations/framework-text.md)
is a new guide: both framework catalogs (`runic-command-line` and Runic SDK's
`runic-views`), how to register and override them, what stays English, a test
self-check, and the German style guide and glossary.

## Dependency ranges

- **Hosting and Wpf are bounded to the Translations minor.**
  `Runic.Translations.Hosting` and `Runic.Translations.Wpf` depended on any
  `Runic.Translations` from their own version up, so an application could update
  `Runic.Translations` to a new minor and keep an older Hosting without a
  warning. They now depend on `[0.10.0, 0.11.0-0.0)`, as
  `Runic.Translations.CommandLine` and every library packed with
  `Runic.Translations.Build` do; a mismatch is `NU1608` at restore.
- **One bound form.** Every dependency on a package released in lockstep
  (`Runic.Translations`, `Runic.Translations.Hosting`, `Runic.CommandLine`) is
  `[F, next minor-0.0)` before 1.0 and `[F, next major-0.0)` from 1.0. The
  Command Line range is no longer written by hand: the same pack step that bounds
  `Runic.Translations` derives it from the tested version, and the pre-push
  manifest check rejects any other form.

## Tool

- `dotnet-runic-translations --version`, the `serve` handshake and SARIF reports
  (`tool.driver.version`) carry the package version, such as `0.10.0`. They said
  `0.2` in every earlier release.
- The tool runs on Runic Command Line 0.12. Its usage errors in human output
  have no code prefix any more; `--format json` still carries every
  `RTR`/`RTRSUP` code.

## Translations Editor

The editor (not part of the packages) is built on Runic SDK 0.17.1, NuGet and npm,
with `CsWebUi` and `CsWebUi.Native` `[2.5.0-beta.4.9, 3.0.0)`, the floor of
Runic SDK 0.17.1's CS-WebUI host; its exact `2.5.0-beta.4.8` pin was a
downgrade there (`NU1605`). Its tool manifest names `dotnet-runic-translations`
0.10.0, and a test keeps it at the release version.

## Upgrading from 0.9

- **Command-line apps** that use `Runic.Translations.CommandLine`: update
  `Runic.CommandLine` (and `.Spectre`, `.Processes`) to 0.12 together with
  every Runic Translations package to 0.10.0. With Command Line 0.9 the adapter
  no longer restores.
- **Overrides of `runic-command-line`**: some messages changed their inputs with
  Command Line 0.12 (for example `diagnostics.unknownCommand` now takes
  `$command`, and `diagnostics.invalidChoiceHidden` takes `$help`). The build
  checks every override against the packed catalog and reports an override that
  no longer fits (`RTR0016`/`RTR0065`), or names a removed key (`RTR0103`).
- **Tests that compare German or English CLI output** see the new wording and
  the usage line and hint after each usage error.
- **Applications that reference `Runic.Translations.Hosting` or
  `Runic.Translations.Wpf`** update `Runic.Translations` to the same minor; a
  0.9 runtime under a 0.10 Hosting is `NU1608`.

## Release engineering

- CI builds against the Command Line release of the train before it is
  published (the train feed, `eng/train-feed.mjs`); such a run uploads a
  `train-feed` artifact, and Publish preview refuses it.
- Publish preview runs the train compatibility gate (row P-tr of runic-sdk's
  `train-compat.yml`) against exactly the packages it publishes, and publishes
  only when it passes.
