# Runic Translations 0.15.0

Install matching `0.15.0` packages from NuGet and npm: the eight NuGet packages
(`Runic.Translations`, `.Build`, `.CommandLine`, `.Hosting`, `.Tooling`, `.Wpf`,
`.Templates` and the `dotnet-runic-translations` tool) and the three npm
packages (`@runic-artifex/vite-plugin-runic-translations`,
`@runic-artifex/translations-svelte` and `@runic-artifex/translations-sveltekit`).

0.15.0 is the Translations step of the 0.23 release train (Runic Command Line
0.14.0, then Translations 0.15.0, then the Runic SDK 0.23.0).
**`Runic.Translations.CommandLine` 0.15.0 needs Runic Command Line 0.14.**

This release makes generated .NET catalogs smaller and faster to load, keeps
the compiler and the language server fast in catalogs of 20,000 messages, and
shows in the Translations Editor what changed in the source of a stale
translation. It removes two paths that 0.14 deprecated: messages in your own
catalog that override command-line framework text, and language server protocol
revision 1. Packs for applications released before 0.15 now need `--contract`.

Until 1.0 a new minor may contain breaking changes. See
[Upgrading from 0.14](#upgrading-from-014) and
[Versions before 1.0](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.15.0/eng/release/README.md#versions-before-10).

## Highlights

- **Smaller generated .NET catalogs that load faster.** Generated C# embeds
  each locale as binary data and the message table as DEFLATE data (RMF2 runtime
  ABI 5): for the Translations Editor's 1,000 messages in two locales the
  embedded data shrinks from 79.7 to 46.1 bytes per message, a locale is ready
  about 5 times sooner, and a message is built only when it is first formatted.
  Accessors share one body per input type, so a NativeAOT executable grows by
  about 130 bytes per message instead of 198. Rebuild to get it; the 0.15
  runtime still runs code generated by 0.13 and 0.14
  ([details](#smaller-generated-net-catalogs-that-load-faster-rmf2-runtime-abi-5)).
- **Fast in large catalogs.** At 20,000 messages in 10 locales,
  `runic-translations validate` takes about 3.5 s instead of 50 s. The language
  server validates a burst of edits once, in the background, and after an edit
  compiles only what changed (about a quarter of a second for one translation
  file), so hover and completion answer while you type. CI now holds the
  language server to budgets on such a catalog
  ([fixes](#fixes)).
- **What changed in a stale translation's source.** The Translations Editor
  shows the source a translation was approved for next to the current one, with
  the changes marked. `review mark`, `xliff import`, the editor and the language
  server record that text in a new `<catalog>.review-sources.json` beside the
  review file, whose format is unchanged. The CLI also takes dotted message keys
  (`common.cancel`)
  ([details](#what-changed-in-the-source-of-a-stale-review-225)).
- **Packages declare the catalog's languages.** A Runic Desktop application
  without `RunicApplicationLocales` gets the languages of its `runic.json`, so
  `dotnet runic package` declares them in macOS, MSIX and Linux packages
  ([details](#runic-packages-declare-the-catalogs-languages-264)).

## Dotted message keys in the CLI ([#225](https://github.com/Runic-Artifex/runic-translations-sdk/issues/225))

A message has one name for people: its logical key, the dotted path of its groups and name (`common.cancel`), as
`validate` and the editor show it. `review mark --key` now takes it as well as the canonical key that generated code
and the review file use (`common_cancel`). Both name the same message (`RTR0018` keeps them unambiguous), and the
review file keeps storing the canonical key. A key that names no message is reported with the closest logical key
(`Did you mean 'common.cancel'?`), here and in `overrides add --key` and the compile server's `message` and
`set-message`.

The Translations Editor's bridge contract adds, without changing existing members, the logical path of each message
(`EditorMessageEntry.path`, `["common", "cancel"]`) and of the message a diagnostic belongs to
(`EditorDiagnostic.messagePath`), for a namespace tree in the message list.

## What changed in the source of a stale review ([#225](https://github.com/Runic-Artifex/runic-translations-sdk/issues/225))

When a source message changes after its translation was approved, the Translations Editor now shows what changed: the
workflow panel of the stale translation shows the source it was approved for ("Source when marked") next to the
current one, with removed words struck through, added words highlighted and placeholders as chips, beside **Confirm
translation** and **Mark needs review**.

The text comes from a new companion of the review file, `<catalog>.review-sources.json`
(`runic.translations.review-sources/1`, schema `review-sources-v1.schema.json`, packed with Runic.Translations.Tooling
and written by `runic-translations schema`). `review mark`, `xliff import`, the editor and the language server's
**Mark … reviewed** record the MF2 source text of each entry they write there: one text per message key and source
fingerprint, shared by all locales. `xliff import` records the source the XLIFF file was translated from, also when it
has changed since the export. Texts no entry refers to are dropped on the next write.

`<catalog>.review.json` keeps the `runic.translations.interchange-review/2` format unchanged, because the 0.14 readers
refuse unknown members and schemas; 0.14 and 0.15 tools keep working on the same files. An entry recorded without a
text (by an older tool) shows the stale hint without the comparison.

The editor's bridge contract adds, without changing existing members, `EditorReviewSnapshot.recordedSources` (the
recorded text of each stale entry, by key and source fingerprint).

## Runic packages declare the catalog's languages ([#264](https://github.com/Runic-Artifex/runic-translations-sdk/issues/264))

When a Runic Desktop application does not set `RunicApplicationLocales`, Runic.Translations.Build adds the languages
of its `runic.json` as `RunicApplicationLocale` items: `baseLocale` first, as the development language, then
`locales`, without `pseudoLocales`. `dotnet runic package` then declares them in the macOS, MSIX and Linux packages,
and the macOS development bundle of `dotnet run` lists them in `CFBundleLocalizations`, so macOS shows its own text in
the user's language without the languages being listed twice. The items are added during evaluation, which is how
`dotnet runic package` reads the project. A project that sets the property keeps its value, the project's own items
still give a language its name and description, several `runic.json` files add their languages in order, and
`RunicTranslationsFillApplicationLocales` set to `false` turns this off.

## Smaller generated .NET catalogs that load faster (RMF2 runtime ABI 5)

Generated C# embeds each locale in a compact binary encoding instead of JSON, and the message table as DEFLATE data
(RMF2 runtime ABI 5, D077.16). For the Translations Editor's 1,000 messages in two locales the embedded catalog data
shrinks from 79.7 to 46.1 bytes per message; a NativeAOT executable no longer links the JSON reader for generated data
(about 34 KB less) and grows by about 130 bytes per message instead of 143. A locale is ready about 5 times sooner on
first use (the editor's English: 1.6 ms → 0.31 ms), and each message is built only when it is first formatted, so a
message that is never shown keeps about 40 bytes instead of about 490 (the editor: 330 KB less memory after first use,
at about 0.15 µs on each message's first format).

Rebuild to get it: `Runic.Translations` 0.15 runs catalogs generated for RMF2 ABI 3, 4 and 5, so libraries built with
0.13 or 0.14 keep working, and `Runic.Translations.Build` 0.15 still generates ABI 4 for a project that references a 0.14
runtime. The binary encoding is specified byte for byte in
[RMF2 execution profile v2](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.15.0/specs/translations/rmf2-execution-v2.md#generated-locale-data-binary-encoding);
packs and ESM output stay JSON.

## Upgrading from 0.14

Update every Runic Translations package, NuGet and npm, to 0.15.0 together, and
Runic Command Line to 0.14.

- **Runic Command Line 0.14.** `Runic.Translations.CommandLine` 0.15 pairs with
  Runic.CommandLine 0.14: its package depends on `Runic.CommandLine`
  `[0.14.0, 0.15.0-0.0)`, so update both together; 0.14.x of the adapter stays
  on Command Line 0.13 (#243). Command Line 0.14 retires the `faults.RCLI4001`
  key: the `RCLI4001` fault (a prompt that cannot be asked) always shows its
  `diagnostics.prompt-*` text, so every framework key now has a message in the
  built-in English and German catalogs. To change that text, override
  `diagnostics.promptRequiresTerminal`, `diagnostics.promptJsonOutput` and
  `diagnostics.promptDisabled` (input `prompt`) in
  `translations/overrides/runic-command-line/<locale>.rmf2`, and delete a
  `faults.RCLI4001` message. Its strict JSON reader (`CommandJsonEnvelopeReader`
  and the `Runic.CommandLine.Testing` helpers built on it) now rejects a frame
  with a duplicate member name anywhere, also inside members it does not know,
  with `duplicate-property`; write each member name once per object. See the
  [Command Line 0.14 release notes](https://github.com/Runic-Artifex/runic-cli-sdk/releases/tag/v0.14.0).
- **Breaking: a message in your own catalog no longer overrides command-line
  framework text.** 0.14 deprecated this second override path; 0.15 removes it.
  `TranslationCommandTextResolver` asks your application's catalog only for your
  own keys (`DescriptionKey` text), so a message named after a
  `runic-command-line` key, such as `help { usage = Synopsis }`, has no effect,
  and the built-in framework text is shown. The resolver no longer writes its
  trace warning. Warning `RTR0107` now says that the message has no effect and
  names the key (#243). To keep the text, move each such message, unchanged, to
  `translations/overrides/runic-command-line/<locale>.rmf2`, add
  `{ "catalog": "runic-command-line", "from": "Runic.Translations.CommandLine" }`
  to `overrides` in `runic.json`, and register `AppTextCatalog.Overlays` with a
  context-based resolver (`new TranslationCommandTextResolver(context, AppTextCatalog.CatalogId)`,
  the `TranslationContextBuilder` constructor, or `AddRunicCommandLineTranslations()`);
  the snapshot and manager constructors ignore overlays. The build then checks
  each override against the framework catalog (`RTR0103`). If the message is
  your own text that only shares the name, rename it. See
  [Framework text](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.15.0/docs/guides/translations/framework-text.md#messages-named-after-command-line-framework-keys).
- **Use Runic DevKit 0.22 or later with the 0.15 language server.** The language server speaks only protocol
  revision 2 now ([details](#breaking-changes)). Runic DevKit 0.22 and later, for VS Code and Visual Studio 2026,
  always ask for it. The Runic extensions of runic-editors 0.21 and earlier report a palette refactoring (Rename Input,
  Rename Slot, Rename Resource, Extract Group, Inline Resource) as failed although the server made the edit: update
  them. Other LSP clients need no change, and `runicProtocol` can be removed from their configuration
  ([language server guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.15.0/docs/guides/translations/language-server.md#protocol-revisions)).
- **Write packs for releases before 0.15 with `--contract`.** A pack the 0.15 compiler writes for the current sources carries markup contract version 3, which runtimes before 0.15 refuse as `RTR0023/markup-contract-version-mismatch`, also as an overlay and also when the catalog's contract fingerprint has not changed. For an application released with 0.14 or earlier, build its packs with `generate --emit-json --contract <its shipped locale artifact>`, which keeps that release's version 2 contract ([over-the-air guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.15.0/docs/guides/translations/ota.md#packs-for-a-shipped-release)).

### Breaking changes

- The language server no longer speaks protocol revision 1, the Translations 0.13 behaviour that 0.14 kept for a
  client without `initializationOptions.runicProtocol: 2`
  ([#263](https://github.com/Runic-Artifex/runic-translations-sdk/issues/263)). Every client gets revision 2, and
  `runicProtocol` is ignored: `runic.renameResource`, `runic.renameInput`, `runic.renameSlot`, `runic.extractGroup`
  and `runic.inlineResource` apply their edit through `workspace/applyEdit` and return `null` (a client without
  `workspace.applyEdit` still receives the `WorkspaceEdit`); `prepareRename` and the `refactor.extract` and
  `refactor.inline` code actions are always offered; an unknown request is `MethodNotFound` (-32601) instead of
  `null`, and a request that cannot be carried out is `RequestFailed` (-32803) instead of `InvalidParams`;
  `serverInfo.version` is the tool's version instead of `1`; and the server registers its file watchers, or watches
  the workspace itself, for every client.

### Behaviour and output changes

- Diagnostics name a message by its logical key (`common.cancel`) instead of its canonical key (`common_cancel`):
  `RTR0090` and the `review mark --key` command it suggests, `RTR0016`, `RTR0021`, `RTR0062`, `RTR0069`, `RTR0070`–`RTR0074`,
  `RTR0076` and `RTR0078`, as `RTR0010`, `RTR0011` and `RTR0094`–`RTR0098` already did. Diagnostic IDs, locations and
  the structured message key (still the canonical key) are unchanged; a check that matches the text of these
  diagnostics needs updating. A key without groups reads the same in both forms.

- `review mark`, `xliff import`, the Translations Editor and the language server's **Mark … reviewed** also write
  `<catalog>.review-sources.json` beside `<catalog>.review.json`, with the source text of each review entry they
  record. Commit it with the review file. The review file's own content is unchanged.

- Generated output and packs carry markup contract version 3, version 2 without the message entries of the default shape (no slots, not structured, inline content, each locale its own content locale), with the catalog's locales listed once instead (D077.16). This changes the C# a project generates for a 0.15 runtime, the ESM output's `dynamic.js` (`rmf2Contract`) and every locale artifact and pack; message modules are unchanged. Both runtimes read versions 2 and 3 and compare them as one contract, so a 0.15 application loads the version 2 packs written for it, as exact packs and as overlays. C# generated for a runtime before 0.15 keeps version 2, and the caller fingerprint does not change. The format is in [RMF2 execution profile v2](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.15.0/specs/translations/rmf2-execution-v2.md#markup-contract-version-3).

- Generated C# accessors with one input call one shared body per input type (`__Format_string`, `__FormatContent_int64` and so on), and those with several inputs pass their arguments as a collection expression, a span on the stack. A call no longer allocates an argument array, and a NativeAOT executable grows by about 143 bytes per message instead of 198 (the size probe, 30 % of its messages with inputs). Public members, their signatures and `GeneratedNameVersion` are unchanged; only the generated private members differ, so rebuild to get the smaller code.

## Fixes

- An MF2 expression that cannot be read, such as one left behind by an unbalanced brace in a message, reports one error and the compiler continues after it, instead of adding several errors for each remaining character of the expression. A stray `{$oops` in one plural variant now gives two errors instead of 14.
- Authoring a message under an existing group inserts it into that group instead of writing a second block for the same group (the translations editor and `CreateResource` both did this for nested keys).
- The language server's "Mark … reviewed" code action names the message by its dotted path (`notes.pinned`), as RTR0090 and the command line do, instead of its flattened key (`notes_pinned`).
- The language server answers a pending request with `ContentModified` (-32801) only when a change sent while it was
  pending makes its result stale ([#250](https://github.com/Runic-Artifex/runic-translations-sdk/issues/250)). Before,
  any open, change, close, watched-file or configuration event refused every pending document request, so saving a
  file could leave an empty outline, no code actions or a failed `runic/message`. The outline, folding, semantic tokens
  and formatting now depend on their own document only; hover, completion, the code-action listing, `runic/message` and
  `runic/documentInfo` also on `runic.json`, review files and restore state; rename, definition, references, code-action
  resolve and commands also on every file of the catalogs they read, so edits are still never computed from outdated
  text. A watched-file event for an open document whose file holds its text, as after a save, changes nothing. See
  [Protocol](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.15.0/docs/guides/translations/language-server.md#protocol).
- The compiler scales linearly with the size of a catalog. At 20,000 messages × 10 locales, `runic-translations validate` takes about 3.5 s instead of 50 s, and the language server shows the first diagnostics of a newly opened file about four times sooner. Two lookups scanned all the messages, or all the lines of a file, once for each message; every message was parsed twice; and files are now read, and messages compiled, on all processor cores. Diagnostics and generated files are unchanged.
- The language server validates a catalog again after an edit without compiling all of it again: unchanged files are not read again, unchanged messages are not compiled again, and only the checks across locales of the edited messages run again. At 20,000 messages × 10 locales, the validation after an edit to one translation file takes about a quarter of a second, and after an edit to a base-locale file about 0.4 s, instead of a full compile. The diagnostics are the same as a full compile's. In a catalog with a review file, the source fingerprints that mark outdated reviews are computed again only for the edited messages, and the review compiles of a catalog with errors reuse the validation's work, so an edit there is validated in about half a second instead of 2.5–4.5 s. The language server also keeps less memory for a large catalog: about 0.75 GiB at 20,000 messages × 10 locales after opening a file, instead of 1.3 GiB, with a peak of 1.2 GiB instead of 2.8 GiB.
- The language server stays responsive in large catalogs ([#271](https://github.com/Runic-Artifex/runic-translations-sdk/issues/271)):
  - It validates a burst of edits once, at the last one. Before, every keystroke queued a full validation of the
    catalog, and in a catalog of 20,000 messages in 10 locales a hover after five keystrokes waited almost five minutes.
  - It validates in the background, cancelling a validation that a newer edit makes outdated. Hover, completion, the
    outline and the code actions are answered while it runs. Diagnostics arrive when the validation of the latest text
    finishes. Hover shows the contract of the latest finished validation.
  - A catalog that does not compile is no longer compiled a second time for its review state unless it has a review
    file, and saved sources are not read again for every request.
  - Hover, completion, definition and references keep one compiled workspace per project between requests and parse an
    edited document once. In that catalog, a hover or completion after five keystrokes takes about 10 ms instead of
    about 40 ms.
- A generated catalog no longer leaves its locale data's inflate buffers in `ArrayPool<byte>.Shared` after a locale's first use. The pool kept a power-of-two array of at least the inflated JSON and a copy of the DEFLATE data for the life of the process, about twice the inflated data: 557 KB for the Translations Editor's 1,000 messages and about 8.7 MB for a catalog of 20,000. The locale data is now inflated into an array of exactly its length, which is collected once the values are read; first use takes as long as before.

## Release engineering

- CI checks the language server's performance on a catalog of 20,000 messages in 10 locales
  ([#262](https://github.com/Runic-Artifex/runic-translations-sdk/issues/262)): the new *Language server / large-catalog
  budgets* job measures open to diagnostics, an edit to its diagnostics, hover and completion while typing, a rename and
  memory over stdio, with and without a review file, and fails when one exceeds its budget (`tests/lsp-budget`,
  `bun eng/run.mjs lsp-budget`). It replaces the opt-in 2,000-message benchmark, which no workflow ran. The language
  server guide lists the budgets and the measured values
  ([Performance](https://github.com/Runic-Artifex/runic-translations-sdk/blob/v0.15.0/docs/guides/translations/language-server.md#performance)).
- The NativeAOT size budget `aot/translations/per-message-bytes` measures the generated catalog apart from the size probe's own code (`tests/aot-size`): the probe formats each message from its own non-inlined method and leaves `Main` and those methods out of the catalog's records. The budget no longer moves with how much ILC inlines into one large `Main`; a catalog costs 67 bytes per message there, of which 46 bytes of the former 113 were the probe's call sites.
