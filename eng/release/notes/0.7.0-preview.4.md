# Runic Translations 0.7.0-preview.4

## Behaviour changes

- **`:integer` and `:number` now group digits by default**, as Unicode
  MessageFormat 2 and `Intl.NumberFormat` do. `{$n :integer}` with 1234 used to
  format as `1234` in every locale; it is now `1,234` in English and `1.234` in
  German, and `{$h :number}` with 12345.5 is `12,345.5` instead of `12345.5`.
  To keep the old output, write `useGrouping=never`
  (`{$n :integer useGrouping=never}`), which also keeps an integer's
  invariant `-1234`. Rebuild C# and regenerate ESM output to pick up the change
  ([#98](https://github.com/Runic-Artifex/runic-translations-sdk/issues/98)).
- `useGrouping` is available on `:integer` and `:number` with the MF2 values
  `auto` (default), `always`, `never` and `min2`. `auto` groups by the content
  locale's CLDR `minimumGroupingDigits`, now part of the pinned CLDR 48.2
  subset: Spanish and Italian keep `1234` and group `12.345`, the other
  supported locale families group `1,234`. `min2` groups only from five
  digits, `always` from four. The .NET and ESM runtimes apply the same rule; a
  new cross-runtime corpus, `rmf2-grouping-conformance.json`, checks them
  against `Intl.NumberFormat`. `auto` and `min2` used to be `RTR0065` on
  `:integer`, and any `useGrouping` was `RTR0065` on `:number` (#98).
- Unless `useGrouping=never`, a negative `:integer` uses the locale's minus
  sign, as `Intl.NumberFormat` does: `−5` in Swedish and Norwegian, where it
  used to be `-5`. Generated ESM now also writes the locale's minus sign for a
  negative `:number`, as .NET already did (#98).
- In a .NET process with `InvariantGlobalization`, `:integer` and `:number`
  format with the invariant symbols (`1,234`) instead of throwing
  `TranslationFormatException`: such a process has no locale data. `:number`
  used to throw there, and `:integer` now needs the locale for its default
  grouping (#98).

## Generated C# catalogs

- Reading a locale of a generated catalog costs about a tenth of the memory it
  did. The embedded data is now read as it streams, into the compact message
  model, without a JSON document or per-message member dictionaries, and
  equal names share one string. The compiler validated the messages when it
  generated the catalog, so the runtime no longer validates them again; the
  catalog still checks each against its definition. For a catalog of 1,287
  messages, `CreateManager("en")` and one message allocated 11.3 MiB and kept
  3.4 MiB live; it now allocates 1.3 MiB and keeps 0.95 MiB. With `de`, which
  also reads `en`, 19.8 MiB and 4.3 MiB became 2.2 MiB and 1.6 MiB. Published
  with NativeAOT, the process's anonymous resident memory after formatting one
  message fell from 14.1 to 3.6 MB (`en`) and from 21.4 to 5.1 MB (`de`), and
  the executable shrank by 1 MB. Rebuild to pick up the change; the generated
  code is unchanged
  ([#97](https://github.com/Runic-Artifex/runic-translations-sdk/issues/97)).
- `CompiledTranslationLocale.ReadRmf2Values` checks the shape, kinds, types and
  limits of the data, but no longer the message semantics. It is for
  generated code; build a `CompiledRmf2Message` with its constructor to
  validate a model from another source (#97).
- RMF2 number literals are read without a regular expression, so the runtime
  no longer builds one (#97).
