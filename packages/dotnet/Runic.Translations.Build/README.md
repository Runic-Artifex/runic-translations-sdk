# Runic.Translations.Build

Connect a conventional Runic MF2 project to MSBuild. The package discovers the
project, feeds its inputs to the typed C# source generator, and can invoke a
pinned local tool to produce locale-v5 JSON or the ESM ABI-4 package.

## Install

```bash
dotnet add package Runic.Translations.Build --version <VERSION>
dotnet new tool-manifest --output .config
dotnet tool install dotnet-runic-translations --version <VERSION>
```

Replace `<VERSION>` with the current version shown on NuGet. The package targets .NET 10, bundles the incremental source generator, and takes no `Microsoft.Build` package dependency. The generator needs a Roslyn host on .NET 10, such as `dotnet build` with the .NET 10 SDK; see the [generator notes](https://github.com/Runic-Artifex/runic-translations-sdk/blob/main/packages/dotnet/Runic.Translations.Generator/README.md#install). Keep it and `dotnet-runic-translations` on one version, and reference `Runic.Translations` at that version or later: code generated by release N runs on runtime N or later within the same minor before 1.0, and within the same major from 1.0. When you pack a library that uses this package, also a multi-targeted one, its `Runic.Translations` dependency gets the range `[N, next minor-0)` before 1.0, for example `[0.9.0, 0.10.0-0)`, and `[N, next major-0)` from 1.0, in the package and its symbol package. The `-0` bound keeps the next breaking release's previews out too, and an application on a runtime outside the range gets NU1608. A version in another format, such as `0.9.*`, stays open with warning RTR0093; set `RunicTranslationsStampRuntimeRange` to `false` to keep NuGet's open range.

## Configure a project

Place `runic.json` and locale message directories under `translations/`. No
MSBuild items are required:

```xml
<PropertyGroup>
  <RunicTranslationsEmitEsm>true</RunicTranslationsEmitEsm>
</PropertyGroup>
```

```bash
dotnet tool restore
dotnet build
```

The project declaration and messages become Roslyn `AdditionalFiles` with
`RunicTranslationKind` metadata for `Runic.Translations.Generator`. ESM output
defaults to `obj/<configuration>/<target-framework>/translations/app.esm-v5/`
and `web-module-manifest-v3.json`; consume it with the Vite adapter.

## Libraries: pack the catalog, override library text

A component library that ships a catalog sets
`<RunicTranslationsPackCatalog>true</RunicTranslationsPackCatalog>`. `dotnet pack`
then adds `runic/<catalog>/` (its `runic.json`, sources and `contract.json`) and
`buildTransitive/<PackageId>.props`, which declares the packed catalog as a
`RunicTranslationsPackedCatalog` item to every project that references the
package. Name the catalog after the package in lower case (`RTR0105` warns
otherwise); `runic-` catalog IDs are reserved for the Runic packages
(`RTR0106`, which relies on nuget.org reserving the `Runic.` ID prefix for the
Runic organization). NuGet imports `buildTransitive/<PackageId>.props` instead
of `build/<PackageId>.props`, so when the library packs its own
`build/<PackageId>.props`, the generated file imports it; its settings then
also reach projects that reference the library transitively. A library that
packs its own `buildTransitive/<PackageId>.props` sets
`RunicTranslationsPackCatalogProps` to `false` and imports
`../runic/<catalog>/catalog.props` from it; packing fails with `RTR0104`
otherwise. Packing removes the package's dependency on
`Runic.Translations.Build`, a development dependency.

An application overrides a packed catalog in its own `runic.json`:
`"overrides": [{ "catalog": "acme.grid", "from": "Acme.Grid" }]` (or
`"from": ["Acme.Grid", "@acme/grid"]` when a Vite build shares the file and the
library ships an npm package too), with the override sources in `translations/overrides/acme.grid/<locale>.rmf2`, which are
not part of the application's catalog. The source generator validates them
against the packed catalog (`RTR0103`, `RTR0104` and the usual translation
checks) and compiles them into `AppTextCatalog.Overlays`, which the application
attaches with `TranslationContextBuilder.AddOverlays`. An override of a key the
library no longer has fails the build (`RTR0103`): delete it when you update the
library. Only packed catalogs of referenced packages can be overridden; a
library referenced with `ProjectReference` reports `RTR0104`. See
[Catalogs from libraries](https://github.com/Runic-Artifex/runic-translations-sdk/blob/main/docs/guides/translations/composition.md#build-time-overrides).

## Check WPF XAML at build time

For a WPF project with a local `RunicTranslationProject`, declare the catalog used by
its default source (the `catalog` value from `runic.json`):

```xml
<PropertyGroup>
  <RunicTranslationsXamlCatalog>app</RunicTranslationsXamlCatalog>
</PropertyGroup>
```

The catalog can also come from a project the WPF project references directly,
for example a class library that holds the ViewModels and the
`translations/runic.json` they use. The referenced project generates and owns
`AppText`, and the build checks the application's XAML against that catalog
without generating it again. That project must import these build targets as
well, as it does to generate the catalog. A local catalog takes precedence over a
referenced catalog with the same ID. Set `RunicTranslationsXamlReferencedCatalogs` to
`false` to skip the referenced catalogs.

`Page` and `ApplicationDefinition` items in `UseWPF=true` projects are scanned
automatically. Static `{rt:Message application_title}` and long-form
`Message`/`MessageInput` declarations are checked against the generated readable
surface: exact key, input count, readable parameter names and plain content kind.
Static `rt:TranslationProperties.RichMessage` keys are checked for inline rich
content. Namespace aliases and nested/quoted markup-extension arguments work;
Binding values are not evaluated. Errors `RTR0080`–`RTR0083` include the XAML
file and line. A message with two or more inputs bound by position (`Arg0`..`Arg3`)
gets warning `RTR0084`, which shows the positional order; use named `MessageInput`
entries instead. The check uses the compiler's existing catalog and readable-name
policy, with no additional runtime contract or WPF dependency in the generator.

The catalog setting is an assertion about the source your application provides;
it does not create a source. An explicit source may select a different catalog,
so the keys it applies to are not checked against the project default: a
`Message.Source` excludes only that message, an attached
`TranslationProperties.Source` excludes its element's content and the file's
templates, styles and resources (which may be instantiated under it), and a
Setter using its static dependency property excludes the whole file. Each such
source is reported once as the informational `RTR0085` with its line. The rest of
the file is still checked. A source that names its catalog is certain: a
`{rt:Message key, Catalog=id}` and the content under an attached
`rt:TranslationProperties.Source="{rt:CatalogSource id}"` are checked against
that catalog when it is the local or a referenced project's catalog, and
reported once as `RTR0085` otherwise. `Binding.Source` selects binding data and does not
affect catalog checks. To assert a known local catalog for such a file, or to check
an explicitly selected file outside WPF, use:

```xml
<ItemGroup>
  <RunicTranslationXaml Include="Views/Checkout.xaml" Catalog="app" />
</ItemGroup>
```

A per-file `Catalog` assertion also covers explicit sources in that file. The
catalog must be the local `RunicTranslationProject` catalog or a directly referenced
project's catalog; external catalogs are not loaded by this check. Without a catalog assertion, only declaration mistakes
that do not require a catalog (missing Key, duplicate/mixed/gapped inputs) are
checked. Keys and input names from bindings, resources or `x:Static`, and dynamic
input collections, retain runtime validation. For rich messages, argument/slot
values remain runtime checks or typed C# checks. This scan does not type-check
Binding results or arbitrary XAML; WPF continues to compile and load it.

The scan only sees one file at a time. A file without its own source
declaration is checked against `RunicTranslationsXamlCatalog`, even if at runtime it
inherits `TranslationProperties.Source` from a parent in another file (for
example a `UserControl` placed in a window that selects an external catalog), an
`App.xaml` style, or code-behind. Skip such a file with item metadata on the
item that selects it:

```xml
<ItemGroup>
  <Page Update="Views/OrderSummary.xaml" RunicTranslationsValidateXaml="false" />
  <!-- or, for an explicitly selected file -->
  <RunicTranslationXaml Include="Views/Report.xaml" RunicTranslationsValidateXaml="false" />
</ItemGroup>
```

A `Catalog` other than the local one is reported as `RTR0080` rather than
skipped, so that a misspelled assertion is not silently ignored.

Design-time content is not checked: attributes and elements in namespaces listed
by `mc:Ignorable` (such as `d:`) are skipped, as is everything inside
`mc:AlternateContent`, because the branch WPF compiles depends on the namespaces
it understands. The Runic and WPF namespaces stay checked even when listed.
Runic declarations are recognized through the
`https://runic-artifex.eu/xaml/translations` URI that Runic.Translations.Wpf
defines with `XmlnsDefinition`, or through the
`clr-namespace:Runic.Translations.Wpf` mapping, with or without
`;assembly=Runic.Translations.Wpf`.

Set `RunicTranslationsValidateXaml=false` to disable the optional scan. It requires
neither artifact emission nor the CLI tool. The translation sources and XAML
must be in the same generating C# project; a precompiled catalog from a library
is an unresolved external catalog. XAML is checked only after the catalog links:
it is skipped while the translation sources have errors (those are reported
instead), when the project does not supply exactly one `RunicTranslationProject`, and
when the referenced runtime lacks the readable surface (`RTR0068`). XAML edits
revalidate only the edited file; they do not regenerate C# sources.

## Select generated artifacts

Set one or more of these properties to `true`:

| Property | Output |
|---|---|
| `RunicTranslationsEmitJson` | `{catalog}.{locale}.locale-v5.json` plus `asset-manifest-v1` |
| `RunicTranslationsEmitEsm` | Cohesive ESM-v5 modules, declarations, and `web-module-manifest-v3.json` |

`RunicTranslationsPseudoLocales` controls the development pseudo-locales that
`runic.json` declares in `pseudoLocales` (`en-XA`, `ar-XB`), for the generated C#
and the JSON and ESM artifacts alike. It defaults to `true` when `Configuration`
is `Debug` and `false` otherwise, so release builds and packages leave them out.
See [Pseudo-locales](https://github.com/Runic-Artifex/runic-translations-sdk/blob/main/docs/guides/translations/rmf2.md#pseudo-locales).

`RunicTranslationsGenerateOnBuild=true` with no individual selection emits the JSON
and ESM groups; C# remains source-generator owned. Generated C# is never written
to disk by this package—it belongs to the source generator.

Every public property, item and metadata name starts with `Runic`. The names
from before 0.8 (`TranslationsOutputPath`, `TranslationProject`, …) and the
retired `TranslationsEmitTypeScript`, `TranslationsEmitTemplateManifest` and
`TranslationsEmitCpp` selections fail the build with
[`RTR0086`](https://github.com/Runic-Artifex/runic-translations-sdk/blob/main/docs/guides/translations/diagnostics.md#rtr0086),
which names the replacement.

Choose this package for generated C# and whenever MSBuild owns input classification or non-C# artifact generation. Use the CLI directly when generation is owned by Vite, CI, or another host.

## Report unused messages

Set `<RunicTranslationsReportUnusedMessages>true</RunicTranslationsReportUnusedMessages>` to report, as the
information `RTR0100`, every message that no C# code of the project references through its readable member,
encoded member, `References` factory or key property, including generated code such as the `.g.cs` files of XAML
or other source generators (only the catalog's own generated types are skipped). The analyzer runs at the end of a
full compilation: `dotnet build -v:n` (or a binary log) and full-solution analysis in the IDE show it. Messages used
only by a key string, from XAML markup that no generated code reads, from another assembly or from the web are
reported too, so read the list as candidates. The web side
has `reportUnused` in `@runic-artifex/vite-plugin-runic-translations`.

## Important build behavior

- Discovery follows the declared `RunicTranslationProject` directory, including nondefault paths. Explicit `RunicTranslationMf2` items override corresponding discovery. File membership is recorded in generation state so additions and removals invalidate artifacts.
- The current target accepts exactly one `runic.json` project and either direct `.mf2` messages or recursive grouped `.rmf2` sources. Mixed representations are rejected.
- The default launcher is the project-local `dotnet tool run runic-translations --`; restore the committed tool manifest before building.
- Output must resolve beneath `IntermediateOutputPath`. Unsafe paths fail with `RTR0020`.
- Incremental generation tracks inputs, settings, the tool manifest, declared outputs, and an owned-output inventory.
- Clean and changed-output reconciliation remove only validated files owned by the integration; unrelated files are preserved.
- Generated files are exposed as `@(RunicTranslationsGeneratedFile)` and default beneath `$(IntermediateOutputPath)translations`.
- Hook points: order your own targets with `BeforeTargets`/`AfterTargets` against `RunicTranslationsGenerateTranslationArtifacts` (runs before `BeforeCompile`), `RunicTranslationsCollectTranslationArtifacts` (runs after it and fills `@(RunicTranslationsGeneratedFile)`) and `RunicTranslationsCleanTranslationArtifacts` (runs before `CoreClean`). `RunicTranslationsGetXamlCatalogSources` is a protocol target that the XAML check calls on referenced projects built with the same release; do not call or hook it. Targets whose names start with `_` are internal.
- Each translation diagnostic appears once, with its help link. In a C# project the source generator reports them during compilation, so the tool run that emits JSON or ESM omits them (it is started with `RUNIC_TRANSLATIONS_OMIT_SOURCE_DIAGNOSTICS=true`), writes no artifacts when they include errors, and leaves the failure to the compilation instead of adding `MSB3073`. In other projects the tool's own `file(line,col): error RTR....` lines are the diagnostics. Any other tool failure is reported as one error naming its exit code.

## RMF2

The bundled .NET MSBuild task discovers recursive `{locale}.rmf2` files,
direct `.mf2` messages, and explicit `sourceRoots`, including membership changes.
It uses the host Microsoft.Build.Framework assembly. Source-checkout imports
require building this package first. See the [RMF2 guide](https://github.com/Runic-Artifex/runic-translations-sdk/blob/main/docs/guides/translations/rmf2.md).
